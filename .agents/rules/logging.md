# ログ出力ルール

ログレベル設計と出力量の指針を定める。INFO レベルのログは「1 万件処理しても人間が読める量か」を判断基準とする。本文中のコード例は `loguru` を前提としているが、レベル設計(TRACE / DEBUG / INFO / WARNING / ERROR の使い分け)の原則は標準の `logging` や `structlog` など他のロガーでも共通である。

> **プロジェクト固有:** 実際に使用するロガーライブラリ、設定ファイルのパス、`[log]` セクションの形式は導入先で追記する。

## 核心ルール

- **INFO レベルでは 1 件ごとのログを出さない。** バッチ処理のサマリーだけを INFO で出力する。
- **DEBUG レベルは「デバッグ時に読める量」を保つ。** 1 操作で数百件以上出力される個別アイテムの詳細は TRACE へ回す。
- **ロガーは 1 系統に統一する。** アプリケーションコード内で標準 `logging` とサードパーティ製ロガー(`loguru` など)を混在させない。混在すると、片方の出力先設定(ファイル出力、フォーマット、レベルフィルタ)がもう片方に適用されず、事後調査時にログが欠落する。

## ロガーの統一

プロジェクトで採用するロガーライブラリを 1 つ選び、アプリケーションコード全体で統一する。標準 `logging.getLogger()` とサードパーティ製ロガーが混在すると、次の問題が生じる。

- 片方の出力先(ファイル出力など)しか設定していない場合、もう片方のログが記録されない。
- 例外情報の付与方法がロガーごとに異なる。たとえば標準 `logging` の `exc_info=True` が、サードパーティ製ロガーでも同じ意味を持つとは限らないため、トレースバック付与は採用ロガーの正しい API を使う必要がある。
- 初期化タイミングに注意が必要である。ロガーの初期化関数が呼ばれる前(モジュールインポート時など)に出力されたログは、設定適用前に評価されて出力先へ乗らないことがある。モジュールレベルの初期化ログは、初期化関数の実行後に処理が走るタイミングまで遅延させる。

> **プロジェクト固有:** 採用するロガーライブラリ名、初期化関数の場所、標準 `logging` とのブリッジが必要かどうかは導入先で追記する。

## プレースホルダ形式の統一

ロガーの遅延フォーマット機構に対して、そのロガーが対応していないプレースホルダ形式を渡すと、値が展開されずログに残らない(例:`{}` 形式を期待するロガーに `%s` 形式の文字列を渡す場合、またはその逆)。

使用するロガーのプレースホルダ形式を統一し、混在させない。f-string へ全面的に書き換えるよりも、既存の呼び出し形式を保ったままプレースホルダだけを揃える方が差分が小さく、不要な文字列評価も防げる。

## ログレベル定義

### TRACE:個別アイテムの大量詳細ログ(既定では抑制)

DEBUG より下位のレベルである(`loguru` なら `logger.trace`、標準 `logging` なら独自レベルを追加するか DEBUG を細分する)。設定ファイルで明示的にレベルを下げたときだけ出力される。1 操作で数百〜数千件出る個別アイテムの詳細をここに置き、通常のデバッグ(`level = "DEBUG"`)で重要な情報が埋もれないようにする。

```python
# 正しい: 1操作で大量に出る個別アイテムの詳細は TRACE
logger.trace(f"パス解決: {stored_path} -> {resolved}")          # 対象ごと
logger.trace(f"Formatted output: fields={n}, ...")             # 対象ごと
logger.trace(f"  モデル読込: name={model.name}, ...")           # モデルごと (数百件)
logger.trace(f"Selection changed: {item_id} = {state}")         # UI操作ごと
```

### DEBUG:開発者向け診断情報(操作・コンポーネント単位)

- 操作単位の処理詳細、分岐結果、関数の入出力(1 操作あたり多くても十数件に収まるもの)を出力する。
- 1 回の選択イベントや 1 ページ描画など、ユーザー操作単位の診断情報を出力する。
- **1 操作で数百件以上に膨らむ個別アイテムのログは DEBUG ではなく TRACE に置く。**

```python
# 正しい: 操作単位は DEBUG
logger.debug(f"レコードをDBに追加: ID={record_id}")
logger.debug(f"重複検出: ハッシュ一致 ID={existing_id}")

# 禁止: オブジェクト生成のたびに出る初期化ログを DEBUG で出さない(削除する)
logger.debug(f"Widget initialized for: {name}")  # インスタンス生成ごと → 削除
# 禁止: 正常系を毎回確認するログ(異常系のみ残す)
logger.debug(f"レコード {id} を発見(正常な状態)")  # → 削除、見つからない時だけ残す
```

### INFO:運用者向けの操作記録

以下のイベントだけを INFO で記録する。
- アプリケーションの起動と終了
- コンポーネントの初期化完了(1 回限りのもの)
- バッチ処理の開始と完了サマリー(件数や結果統計)
- ユーザー操作の開始(ディレクトリ選択、ワーカー起動など)
- 設定ファイルの読み込み

```python
# 正しい: バッチサマリーは INFO
logger.info(f"登録対象: {total}件")
logger.info(f"登録完了: 成功={ok}, スキップ={skip}, エラー={err}")
logger.info(f"バッチ処理開始: {directory}")
logger.info("初期化完了")

# 禁止: 個別アイテムを INFO で出さない
logger.info(f"レコードをDBに追加: ID={record_id}")  # DEBUG にすべき
logger.info(f"処理済みファイルを保存: {path}")  # DEBUG にすべき
```

### WARNING:予期しないが継続可能な状況

以下の状況を WARNING で記録する。
- リソースが見つからない(フォールバック動作がある場合)
- 重複データの検出(処理を続行する場合)
- 外部サービスの一時的な障害
- API キー未設定

```python
logger.warning(f"モデル '{name}' がDBに見つかりません")
logger.warning("利用可能なAPIキーがありません")
logger.warning(f"ハッシュが一致するレコードが既に存在: ID {existing_id}")
```

**正常系で件数などのしきい値を超過しただけでは WARNING にしない。** 検索結果が大量にヒットした、処理対象件数が多いといった「処理は成功しているが規模が大きい」状態は異常ではない。UI 側で注意表示を行う場合でも、ログレベルは UI 表示と独立して判断する。実際に処理が失敗した、入力が不正だった、タイムアウトしたなど、本当に調査が必要な事象だけを WARNING 以上とする。量が多いだけの正常系は INFO(運用上の観測値として残したい場合)または DEBUG に置く。

### ERROR:操作の失敗

以下の失敗を ERROR で記録する。必ずスタックトレース付きで出力する(`loguru` の場合は `exc_info=True`)。
- データベース操作の例外
- ファイル I/O の失敗
- 外部 API 呼び出しの失敗

```python
logger.error(f"登録に失敗: {path}", exc_info=True)
logger.error(f"DB接続エラー: {e}", exc_info=True)
```

## 禁止パターン

### 1. 多層での重複ログ

同じイベントを複数のレイヤーで重複出力しない。最も適切な 1 箇所だけで出力する。

```python
# 禁止: Repository 層と Service 層の両方で同じ操作をログ出力しない
# repository.py
logger.info(f"レコード追加: ID={id}")  # ここで出すなら
# service.py
logger.info(f"登録完了: ID={id}")  # ここでは出さない

# 正しい: 低レイヤーは DEBUG、高レイヤーのサマリーだけ INFO
# repository.py
logger.debug(f"レコード追加: ID={id}")
# batch_worker.py(バッチ完了時のみ)
logger.info(f"登録完了: {count}件")
```

### 2. 毎回生成されるオブジェクトの初期化ログ

リクエストやアイテム 1 件ごとに生成・破棄されるオブジェクトの初期化は、INFO で出力しない。

```python
# 禁止: リクエストごとに生成されるマネージャーの初期化
logger.info(f"ProcessingManager初期化完了: resolution={res}")

# 正しい
logger.debug(f"ProcessingManager初期化完了: resolution={res}")
```

### 3. ループ内の INFO ログ

ループの中で INFO レベルのログを出力しない。

```python
# 禁止
for item in items:
    logger.info(f"処理中: {item.name}")

# 正しい: ループ外でサマリーを出力する
logger.info(f"処理開始: {len(items)}件")
for item in items:
    logger.debug(f"処理中: {item.name}")
logger.info(f"処理完了: 成功={ok}件")
```

## INFO 出力の判断基準

| 確認項目 | 該当する場合のレベル |
|---|---|
| 1 回限りの操作か | INFO 可 |
| N 件のうちの 1 件を処理するログか | DEBUG(数百件以上なら TRACE) |
| ユーザー操作に対する直接的な応答か | INFO 可 |
| 内部コンポーネントの動作詳細か | DEBUG |
| 運用者が常時監視で確認したい情報か | INFO 可 |
