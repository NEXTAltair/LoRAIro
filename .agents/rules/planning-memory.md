# 計画時の過去知識活用ルール

計画策定時に過去の設計判断や教訓を活用するためのルールである。Plan Mode やブレインストーミング、計画作成のワークフローに適用する。

> **プロジェクト固有:** 本文中の `docs/decisions/`、`docs/plans/`、`docs/lessons-learned.md` は代表的な既定パスの例である。導入先の実パスおよび ADR 索引の生成手順はここに追記する。

## 必須:計画策定前の知識確認

計画を策定する際は、コード調査に着手する**前に**以下の 3 点を確認すること。

### 1. 過去の設計判断(ADR)の確認

- ADR ディレクトリ(例:`docs/decisions/`)の索引ファイルを開き、一覧を確認する。
- 関連する ADR を読む。
- 類似の設計パターンや技術選定の根拠を把握する。

### 2. 教訓の確認

- 過去のバグパターンや教訓を記録したドキュメント(例:`docs/lessons-learned.md`)を確認する。
- 特に同じ領域(アーキテクチャ、テスト、UI、DB、外部連携など)のセクションを重点的に確認する。

### 3. 最新の計画の確認

- 計画置き場(例:`docs/plans/`)にある最新の計画(前回セッションの計画など)を確認する。
- 継続中の計画がある場合は、それを前提として参照する。

## 適用条件

以下の作業では本ルールを適用する。

- Plan Mode での計画策定
- ブレインストーミングや計画作成を伴う設計作業
- 新機能追加、アーキテクチャ変更、設計判断を伴うタスク

## スキップ可能な条件

以下のいずれかに該当する場合は、事前確認を省略してよい。

- 設計判断を伴わない単純なバグ修正(1〜2 ファイル程度の変更)
- 同一セッション内で既に確認済みの場合
- タイポ修正やコメント追加など、設計に影響しない変更

## 計画完了後の知識保存

計画策定が完了したら、重要な設計判断(アーキテクチャ決定、技術選定の根拠、パフォーマンス上の考慮事項、設計パターンの選択など)を以下の場所へ保存する。

### ADR(設計判断)

- ADR ディレクトリに新しい ADR を追加する。
- **索引ファイルは手で編集しない。** frontmatter を単一の情報源(SSoT)とし、生成物の索引を再生成する([documentation-maintenance.md](documentation-maintenance.md) の「機械で守れるものは生成物にする」を参照。運用パターンは `okf-bundle` スキルに従う)。
- **作成中または `Status=Proposed` の ADR は、[git-workflow.md](git-workflow.md) に従い worktree ブランチで隔離する。** `Accepted` または `Implemented` として確定するまで、メインブランチへ直接プッシュしてはならない。

### 教訓(バグパターン)

- 教訓ドキュメントの該当する領域セクションへ追記する。
