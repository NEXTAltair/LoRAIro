# テスト方針ルール

Lint やモデルの既定挙動だけでは決まらない、プロジェクト固有のテスト判断基準を定める。`pytest` の基本的な書き方そのものはここに記載しない。Qt / PySide6 や `pytest-bdd` 固有の注意点については、`pytest-qt-bdd` スキル(導入している場合)を参照すること。

> **プロジェクト固有:** 実際のカバレッジ目標値、CI ワークフローの `pytest` フィルタ一覧表、テスト実行コマンド(Makefile ターゲットなど)、submodule やモノレポ内パッケージごとのテスト実行コマンドは導入先で追記する。

## カバレッジ要件

- **最小カバレッジ**: 75% 以上を目安に維持する(具体的な数値は導入先で調整する)。
- **新機能**: 対応するテストを必ず作成する。
- **バグ修正**: 再発防止のためのリグレッションテストを追加する。

### 閾値を一時的に下げない

カバレッジが閾値を下回った場合でも、**閾値そのものを一時的に引き下げて CI を通過させることはしない**。一時的な引き下げは「CI は通るが実質的なカバレッジは改善していない」状態を正当化し、将来の品質劣化を検出しにくくする。閾値割れの原因(デッドコードやテスト未整備)を特定し、以下の除外・削除基準に従って恒久的に解消する。

### 計測除外(`omit` / `source`)と削除の基準

`coverage` の対象除外(`omit` や `source` 除外)を無秩序に広げると、閾値が品質ゲートとして機能しなくなる。以下の基準に従って判断する。

- **`omit` を許可する対象**(いずれかに該当するコードのみ)
  - `src` 本体から一切参照されない開発補助・ヘルパー
  - 描画専用の GUI コードなど、ヘッドレス CI でのテストが技術的に困難なもの
  - 自動生成コード
- **`omit` を禁止する対象**: サービス層、データアクセス層、設定読み込みなどのコア機能。
- **`source` 除外**(`omit` より強い除外であり、計測対象そのものから外す): 外部 API 呼び出しや重い機械学習モデルのロードなど、ヘッドレス CI 環境で実行できない初期化処理を含むパッケージやモジュールに限る。
- **削除の判断**: `src` 本体からもテストからも参照がないコードは即座に削除してよい。テストからのみ参照されている場合は変更履歴を確認し、復活予定があれば隔離、予定がなければ削除する。判断が難しい場合は `omit` に追加したうえで Issue 化する。

> **プロジェクト固有:** `[tool.coverage.run]` の `omit` および `source` の実際のリストと、それぞれをどの基準で許可したかは導入先の記録(ADR など)を参照する。

## テスト構造

```
tests/
├── unit/           # ユニットテスト(外部依存はモック)
├── integration/    # 統合テスト(内部コンポーネントの結合)
├── gui/            # GUI テスト(pytest-qt など)
├── bdd/            # BDD 振る舞い仕様テスト(pytest-bdd)
└── resources/      # テストリソース
```

テストマーカーは `unit`、`integration`、`gui`、`bdd`、`slow` を基本とする。`tests/bdd/` 配下のテストに対する `bdd` マーカーは `conftest` で自動付与する。

## モック戦略

- **モックするもの**: 外部 API(OpenAI、Anthropic、Google など)、大量ファイルを扱うファイルシステム操作、ネットワーク通信、時刻に依存する処理。
- **モックしないもの**: 内部サービス間の連携(統合テストで検証する)、データベース操作(テスト DB を使う)、Qt の Signal/Slot(配線そのものが検証対象であるため)。

## 決定論的 CI テストと実 API・実モデル検証の分離

PR ごとに必須実行する CI ゲートには、**外部依存の可用性に左右されるテストを含めない**。具体的には以下のテストを CI 必須ゲートから除外し、開発者がローカルで必要時に手動実行するオンデマンド検証として扱う。

- 実プロバイダの API キーを使った実 Web API 呼び出し
- 実モデルのダウンロードや実ローカル推論

### CI 必須ゲートから除外する理由

- 外部プロバイダの障害やレート制限によって PR の成否が左右されてしまう。
- CI トリガーごとに API 利用料金が発生する。
- API キーやシークレットの管理負担が増える。
- プロバイダのレスポンススキーマやモデル可用性が予告なく変化する。
- モデルのダウンロードが CI の実行時間とキャッシュ容量を圧迫する。
- GPU の有無など環境差による実行時間のばらつきが大きく、不安定な失敗の原因になる。

一方で、CLI 起動、設定読み込み、DB や出力ファイルの作成、ワークフローの配線確認などは、外部依存の境界へフェイクまたは mock のバックエンドを注入すれば決定論的に検証できる。これらは CI 必須ゲートに残し、mock 中心のユニットテストだけでは拾いにくい「配線の回帰」を補完する。

`pytest` マーカーで区別する場合の例は以下のとおりである。

```python
@pytest.mark.calls_real_webapi        # 実 API キーで実リクエストを行う。CI から除外する
@pytest.mark.downloads_and_runs_model  # 実モデルのダウンロードと推論を行う。CI から除外する
```

> **プロジェクト固有:** 実 API や実モデルの検証を行う Makefile ターゲット、およびフェイクバックエンドを注入するための環境変数や DI ポイントは導入先の記録を参照する。

## submodule・モノレポ内パッケージのテスト

それぞれ独自の `pytest` 設定を持つ複数の独立パッケージ(submodule など)がある場合は、**`pytest` セッションの境界をパッケージの境界に揃える**。各パッケージを独立した `pytest` セッションとして起動し、単一の実行へ混ぜてはならない。

### 分離が必要かどうかの判断基準

ルートの `conftest.py` が重い外部依存(`torch` や `tensorflow` の動的ロードなど)を回避するために `sys.modules` へモジュールレベルの mock を注入している場合、その mock はテスト収集より前のインポート時点で有効化される。そのため、ルートから対象パッケージ自身のテストまで一緒に収集してしまうと、他パッケージ都合の mock が対象パッケージのテストにも波及し、意図しない失敗を引き起こす。

`conftest` の前提、カバレッジ対象、依存バージョンのいずれかがパッケージごとに異なる場合は、単一の `pytest` 実行に混ぜず、作業ディレクトリをパッケージルートに移して独立したセッションで実行する。

パッケージ間の venv 共有方針については、[parallel-execution.md](parallel-execution.md) の「venv 分離粒度:パッケージ(submodule)間」を参照すること。

> **プロジェクト固有:** パッケージごとのテスト実行コマンド(Makefile ターゲットなど)をここに追記する。

## CI と同等のフィルタによるローカル検証

ローカルでテストを検証する際は、CI ワークフローの `pytest` フィルタと**完全に一致するフィルタ(CI-equivalent filter)**で実行する。`-m unit` のような短縮フィルタだけで「回帰なし」と結論づけてはならない。

### 理由

`pytest` マーカー(`unit`、`standard`、`fast`、`heavy` など)は互いに独立した分類である。`-m unit` で実行しても `-m standard` のテストは収集されないため、CI での失敗をローカルで再現できない(発端となった事例は導入先の記録を参照すること)。

> **プロジェクト固有:** CI ワークフローのジョブごとの `pytest` フィルタ一覧表をここに追記する。CI 側を変更した際は本表もあわせて更新する。

### 適用タイミング

以下のタイミングでは、必ず CI と同等のフィルタで検証を行う。
- submodule の固定バージョンを更新する PR を起票する前
- ライブラリ側の API 変更やリファクタリング PR を起票する前
- 「回帰なし」とユーザーへ報告する前

### 実行例

```bash
cd <package root>
uv run pytest -m "not downloads_and_runs_model and not calls_real_webapi"
```

### フックによる事前チェック

`gh pr create` 実行時に submodule(`submodule_globs` に一致するパス)の固定バージョン変更が含まれる場合、kit のフック(`hook_pre_pr_submodule_check.py`)が CI 同等テストの実行確認を要求する。実行済みであることを明示して通過させるには、コマンド内に `CI-EQUIV-TESTED` マーカーコメントを含める。詳細はフックスクリプトのヘッダーを参照すること。

### worktree・I/O 制約とパッケージテスト

worktree 間およびパッケージ間でどこまで実行環境を共有するかの方針は [parallel-execution.md](parallel-execution.md) に集約している。ネットワークマウント上のチェックアウトなど低速な I/O 環境では、パッケージごとに専用 venv を作ると実用速度を大きく損なう場合があるため、同ファイルのルールに従って共有 venv を優先する。

> **プロジェクト固有:** Dev Container や CI 環境固有のマウント構成、Makefile ターゲットの詳細はここに追記する。

## 遅延インポート化(lazy import)との関係

重いネイティブ依存(`torch` や `tensorflow` など)を遅延インポートへ移行する場合は、対応するスキル(`lazy-import-refactor` など)を用いてテストへの副作用(`@patch("module.torch")` など)を事前に予測し、本セクションの CI 同等フィルタで検証することを義務付ける。
