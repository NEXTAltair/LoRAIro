# ADR 0016: Coverage Threshold Policy

## Context

Issue #131 で `coverage-gate` を新設した結果、長らく努力目標にとどまっていた `fail_under=75` が CI 上で初めて検証された。これにより、合算カバレッジが **58%** であることが顕在化し、75% への到達経路を決める必要が生じた。

### Issue #135 Phase 2 調査の発見

`grep` ベースのインポートグラフ解析により、`src/` 本体から一切参照されないモジュール(デッドコード)が 9 件、計 4,257 LOC(全体 18,420 行の 23%)検出された。

| ファイル | LOC | `src` 参照 | `test` 参照 | 性質 |
|---------|-----|---------|----------|------|
| `gui/widgets/annotation_results_widget.py` | 678 | 0 | 0 | 完全な未使用コード |
| `gui/widgets/annotation_status_filter_widget.py` | 276 | 0 | 0 | 完全な未使用コード |
| `services/ui_responsive_conversion_service.py` | 1,225 | 0 | 1 | テスト経由のみ |
| `gui/widgets/model_selection_table_widget.py` | 397 | 0 | 4 | テスト経由のみ |
| `services/annotator_library_adapter.py` | 179 | 0 | 3 | テスト経由のみ |
| `services/batch_processor.py` | 298 | 0 | 7 | テスト経由のみ |
| `services/batch_utils.py` | 205 | 0 | 4 | テスト経由のみ |
| `services/model_info_manager.py` | 354 | 0 | 33 | テスト経由のみ |
| `services/openai_batch_processor.py` | 345 | 0 | 3 | テスト経由のみ |
| **合計** | **4,257** | **0** | — | **全体の 23%** |

この結果から、カバレッジを 58% から 75% へ引き上げるための 2 つの選択肢が浮上した。

- **短期案**:`fail_under` を 60% へ一時的に引き下げ、CI を成功状態へ戻す。
- **中長期案**:`omit` ルールを整備し、デッドコードの削除と `omit` 化によって 75% を維持する。

また、当時の `[tool.coverage.run] omit` はインフラ層のみを対象としており、アプリケーションコードに対する `omit` 基準が未定義である点も課題であった。

### 判断分岐の影響

場当たり的な緩和を行うと、「カバレッジが下がったら一時的に閾値を下げる」という前例を作ってしまう。これは将来のカバレッジ低下に対する検知感度を下げる恐れがある。

そのため、**`omit` 許可基準**・**削除許可基準**・**`fail_under` 堅持ポリシー**を明文化し、Issue #138–142 群の前提方針として固定する必要がある。

## Decision

1. **`fail_under=75` を恒久的に維持する。**
   段階的な引き下げ(60 → 65 → 70 → 75%)は採用しない。

2. **`omit` 許可基準を定める。**
   以下のいずれかに該当するコードのみ、`omit` の対象とすることを許可する。
   - (a) `src/` 本体から一切参照されない開発補助コードやヘルパー
   - (b) Qt の描画専用 GUI(ヘッドレス CI でのテストが技術的に困難なもの)
   - (c) 自動生成コード(`gui/designer/*` など)

3. **コア機能の `omit` を禁止する。**
   `services/`、`database/`、`storage/`、`configuration_service` などのコア機能は `omit` 対象にできない。

4. **削除許可基準を定める。**
   - `src/` 本体からの参照が 0 かつテスト参照も 0 の場合は、**即時に削除してよい**。
   - `src/` 本体からの参照が 0 でテスト参照のみ存在する場合は、`git log --all -- <file>` で経緯を確認し、次のいずれかで処置する。
     - (a) 機能の復活予定がある場合は `scripts/legacy/` へ移動する。
     - (b) 単なる残存物である場合は削除する。
     - (c) 判断が困難な場合は `omit` へ追加したうえで Issue を起票する。

5. **ポリシー参照を義務化する。**
   `[tool.coverage.run] omit` への新規追加、または `src/` 配下のファイル削除を伴う PR では、コミットメッセージまたは PR 説明で本 ADR(0016)を参照しなければならない。

6. **`source` 除外基準を定める(`omit` とは別概念)。**
   - `omit`:計測対象に含めたうえで、特定ファイルを結果から除外する仕組みである。
   - `source` 除外:計測対象そのものに含めない、より強い除外である。
   - **除外許可条件**:外部 API リクエストや ML モデルロードなど、ヘッドレス CI 環境で実行できない初期化処理を含むローカルパッケージに限り許可する。
   - **現状の適用例**:`image-annotator-lib` は、`torch` や ML モデルのロード処理がヘッドレス CI でハングするため、`tests/conftest.py` でモジュールレベルの `sys.modules` 差し替えによるモック化を行っている。CI 上では 0% となるため、`source` から除外する。
   - **含有例**:`genai-tag-db-tools` は SQLite 操作のみで CI 実行が可能なため、`source` に含める。
   - `source` リストの変更を伴う PR でも、本 ADR(0016)を参照することとする。

## Rationale

### なぜ `fail_under=75` を堅持するか

- Issue #138 単独で +17pt(58% から 75%)の到達が見込めるため、一時的な引き下げ自体が不要である。
- 一時引き下げは「CI は通っているが実質的なカバレッジは改善していない」状態を正当化し、将来の劣化検知感度を低下させる。
- 75% はプロジェクト発足以来の目標値であり、一度でも引き下げると再引き上げの合意形成が難しくなる。

### なぜ omit 許可基準を明文化するか

- Qt のヘッドレス CI でのテストが技術的に困難なコード(`ui_responsive_conversion_service.py` など)と、単なるテスト整備の遅れを明確に区別するためである。
- 新規 PR のレビュー時に、`omit` 追加の可否を一貫した基準で判断できるようにするためである。

### なぜコア機能の omit を禁止するか

- `fail_under` を品質ゲートとして機能させるには、コア機能を計測対象から外さないことが大前提である。
- コア機能の `omit` を認めると、「カバレッジが下がったら `omit` で回避する」という安易な抜け道が生まれてしまう。

### 却下した選択肢

| 選択肢 | 却下理由 |
|--------|---------|
| A:`fail_under=60` への一時引き下げ | CI は成功状態に戻るが実質カバレッジは改善しない。劣化検知感度が低下し、再引き上げも困難になる。 |
| B:段階的引き上げ(60 → 65 → 70 → 75%) | Issue #138 単独で 75% 到達が見込めるため引き下げ自体が不要である。段階管理の運用コストが純粋な負債になる。 |
| C:コアとテスト困難コードで `fail_under` を分離 | `coverage.py` の単一 `fail_under` 設定では実装が難しく、複数回の計測実行により運用が複雑化する。 |
| D:`omit` ポリシーを定義しないまま運用 | PR ごとに `omit` 可否の議論が発生して一貫性が失われ、暗黙ルール化の温床になる。 |

## Consequences

### 良い点

- `omit` や削除の判断に一貫性が生まれ、PR レビューで明確な基準に基づいた議論ができるようになる。
- コア機能のテスト追加が構造的に強制され、`omit` による回避を防げる。
- Issue #138 の実施によって CI の `coverage-gate` が成功状態へ復帰し、以降は 75% 維持が技術的な品質ゲートとして機能する。

### 悪い点・トレードオフ

- `omit` リストを継続的にメンテナンスするコストが発生する。新規の開発ヘルパーを追加するたびに、`omit` の要否を判断する必要がある。
- Qt の描画専用コード(`ui_responsive_conversion_service.py` 相当)は恒久的にカバレッジ計測の対象外となる。ただし、ADR 0009(Qt Decoupling)によりコアロジックは Qt 非依存層へ分離済みであるため、ビジネスロジックの品質は担保される。
- 本 ADR は `pyproject.toml` と対で運用する。`fail_under` を変更する場合は、必ず本 ADR の Status も見直す必要がある。

## Roadmap

Issue #135 に紐づくサブ Issue 群の実施優先順位は以下のとおりである。

| Phase | Issue | 内容 | 期待効果 |
|-------|-------|------|---------|
| **Phase 1(最優先)** | #143(本 ADR) | ポリシー確立 | 判断基準の明確化 |
| **Phase 2(最優先)** | #138 | デッドコード 9 モジュール / 4,257 LOC の処遇判定・削除・`omit` 化 | 58% → **約 75%** |
| **Phase 3(並列実施可)** | #139 | `image_processing_service.py` のテスト新規作成(14% → 75%+) | +約 5pt |
| **Phase 3(並列実施可)** | #140 | `model_registry_protocol.py` のテスト新規作成(34% → 80%+) | +約 2pt |
| **Phase 3(並列実施可)** | #141 | `storage/file_system.py` のテスト拡充(59% → 80%+) | +約 2pt |
| **Phase 3(並列実施可)** | #142 | `configuration_service.py` のテスト拡充(56% → 80%+) | +約 2pt |
| **Phase 4(長期)** | 追加調査 Issue | 定期的なカバレッジ改善 | バッファ確保 |

Phase 1 と Phase 2 の完了で CI が復旧し、Phase 1 から Phase 3 までの完了で 75% から 76.5% へのバッファを確保する計画である。
