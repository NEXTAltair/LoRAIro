# ADR 0061: 登録パイプライン再設計 — pHash 候補の重複/別版分類

- **関連 Issue**: #630 / #631 / #632 / #633

## Context

現在の画像登録処理は、pHash が完全一致した時点で「重複確定」とみなし、新規の `images` レコードを作成せず既存 ID を返している(`ImageRepository.add_original_image` および `ImageDatabaseManager.register_original_image`)。この設計は単純だが、同一 pHash になり得る「別版」まで先行画像へ吸収してしまう問題がある。具体的には次の差分が失われる。

- カラー版とグレースケール版(見た目の彩度が異なるが pHash は一致しやすい)
- 解像度やサイズの違い
- 透過(アルファチャンネル)の有無の違い

加えて、登録パイプラインには pHash 完全一致前提に依存した構造的な課題が 2 点残っている。

1. **保存タイミングの責務(#632)**: `_prepare_image_metadata()` が重複チェックより前に `fsm.save_original_image()` を実行する経路が存在する。その結果、重複スキップされる画像であってもファイルコピーが残り得る。GUI ワーカーは事前の `detect_duplicate_image()` で影響を軽減しているが、`register_original_image()` を直接呼ぶ経路では保存処理が先に走る。
2. **副作用の経路間差異(#633)**: 重複時の関連 `.txt` / `.caption` の取り込み、filename alias 登録、統計値(`registered` / `skipped` / `failed`)の扱いが、GUI ワーカー・API・直接呼び出しの間で揃っていない。

本 ADR は、#630、#631、#632、#633 を含む登録パイプライン再設計全体の設計判断を記録する SSoT である。#631(グレースケール相当判定)はこの再設計の基盤実装にあたる。

## Decision

### 1. pHash 完全一致は「重複確定」ではなく「候補」とする

pHash の完全一致を最終判断にせず、追加の属性比較を経て「重複」か「別版」かを分類する。完全に同一と判断できる場合のみ既存画像へ寄せ、重要な属性差がある場合は別版として新規レコードを作成する。

- **ハミング距離による近似重複検知は導入しない**: pHash の完全一致のみを候補抽出の起点とする。近似検知はしきい値運用が難しく、別版分類という本 ADR の目的とは別軸である。
- **`phash` カラムは unique 化しない**: 候補検索キーとして使用し、複数行が同一の pHash を共有することを許容する。候補検索を高速化するため、`index` は維持する。

### 2. 分類属性

同一 pHash の候補同士を比較し、重複と別版を判定するために次の属性を用いる。

- `width` / `height`
- `has_alpha`
- `is_grayscale_like`(#631 で追加した内容ベースのグレースケール相当判定)

必要に応じて `mode`、`format`、`extension`、`color_space` を補助的に用いる。`colorfulness_score` は閾値調整や診断に使う連続値であり、分類の直接条件には使用しない。

#### `is_grayscale_like` と `colorfulness_score` の判定方式(#631)

`mode == "L"` だけの判定では不十分である。RGB 画像であっても全チャンネルがほぼ同じ値であれば実質的にグレースケールだからである。また、JPEG 圧縮ノイズにより `R == G == B` が崩れるため、完全一致ではなく閾値付きの内容判定を採用する。

- **サンプリングと透過画素の除外**: 画像を RGBA へ変換し、サムネイル化してサンプリングする。完全透過(不可視)の画素は任意の RGB 値を持ち得るため、彩度算出から除外する。これらを含めると見えない色によって誤分類が起きる。
- **彩度スコアの算出**: 可視画素ごとに `max(|R-G|, |G-B|, |R-B|)` でチャンネル間の最大差分を求める。その 99 パーセンタイル(`method="higher"` による実在画素値)を `colorfulness_score` とし、閾値以下なら `is_grayscale_like=True` と判定する。
- **99 パーセンタイルを選ぶ理由**: 平均値ではなく高パーセンタイルを使うのは、ロゴ・透かし・小さなカラー領域のように画像のごく一部にだけ色が乗るケースを「カラー」として残すためである。一方、100 パーセンタイル(最大値)は単一の外れ値画素に過敏なため避け、99 パーセンタイルを採用する。
- **縮小とパレット画像の扱い**: 縮小には面積保存系の `BILINEAR` を用い、罫線や透かしなどの細い色領域を取りこぼさないようにする。パレットモード(`P` / `1`)は Pillow が縮小時に `BILINEAR` を無視して `NEAREST` に切り替えるため、縮小前に RGB へ変換する。また、透過カラーのにじみを防ぐため、縮小前の元アルファを最近傍参照して可視画素のみを採用するガードを入れる。
- **動画像の扱い**: アニメーション GIF や WebP などの動画像は 1 フレーム目のみを評価する。これは pHash 計算や保存処理と同じフレーム基準で整合させるためである。フレーム横断の集約は #631 のスコープ外とし、必要があれば別版分類(#630)側で扱う。
- **パラメータ管理**: 閾値・パーセンタイル・サンプリングパラメータは、`file_system.py` に根拠コメント付きのモジュール定数として定義する。

### 3. 保存タイミングは分類後とする(#632)

pHash 計算後かつ保存前に分類できる構造へ見直す。ファイル保存は分類結果が「新規」または「別版」のときだけ実行する。

- 重複と判定された候補は保存せず、ファイルコピーを残さない。
- 保存済みでありながら DB 登録しないことが確定した場合の後処理規約を定め、保存物を削除して孤児ファイルを残さない。
- GUI・API・直接呼び出しのいずれの経路でも保存タイミングを揃える。
- 重複時に 512px 画像の生成や関連ファイル処理が必要になる場合の順序を明確化する。

### 4. 副作用は分類結果駆動で全経路を統一する(#633)

重複時・別版時・新規時の副作用を 1 箇所で定義し、GUI・API・直接呼び出しのすべての登録経路で同じルールを適用する。

- 関連 `.txt` / `.caption` の取り込み先を分類結果に従わせる。
- filename alias 登録の責務と失敗時の挙動を統一する。
- 統計値(`registered` / `skipped` / `failed`)の意味を経路間で揃える。

### 5. スコープ前提

1 プロジェクトにつき 1 DB を前提とする。プロジェクトを横断した重複・別版判定は対象外とする。

### 6. バックフィル方針(#631)

`is_grayscale_like` と `colorfulness_score` は NULL 許容で追加し、既存 DB に対しては遅延バックフィルを既定とする。

マイグレーション時には全件の再計算を行わない。内容サンプリングを伴うため、起動時の一括バックフィルは処理コストが高くユーザー体験を損なうからである。NULL を「未判定」として扱い、再アノテーションや別版分類など判定が必要になった経路で遅延バックフィルを行う。なお、新規登録では `FileSystemManager.get_image_info` が値を埋めるため NULL にならない。

## Consequences

- **別版登録による行数増加**: 別版を新規登録することで `images` テーブルの行数は増える。ただし 1 DB = 1 プロジェクト前提であり横断スコープを持たないため、増加は局所的であり許容範囲内である。
- **`UniqueConstraint(uuid, phash)` の維持**: `uuid` は登録ごとに一意に発番されるため、同一 pHash の別版が複数行になっても複合制約には抵触しない。`phash` 単独の unique 化は行わない(候補検索キーのため)。
- **経路間不整合と孤児ファイルの解消**: 保存タイミングと副作用が分類結果駆動に統一され、経路依存の不整合(#632 / #633)が解消される。重複スキップ時に孤児ファイルが残らなくなる。
- **制御フローの整理**: 分類ロジックの追加により登録経路の制御フロー自体は複雑化するが、責務が 1 箇所に集約されることで全体の見通しは改善する。

## 実装フェーズ

本 ADR が定める再設計は段階的に実装する。本 ADR の起票時点では基盤(#631)のみを実装する。

- **基盤(#631)**: `is_grayscale_like` / `colorfulness_score` カラムの追加、`get_image_info` での内容判定、`add_original_image` での永続化、Alembic マイグレーション(本フェーズ)。
- **後続**: 候補分類(#630)と保存タイミング見直し(#632)を実施し、その後に副作用統一(#633)へ進む。
