# ADR 0092: クロップ画像の親子関係を専用テーブル crop_relations で保持する

- **関連 Issue**: #1339 (画像クロップ機能), #1343 (親子関係テーブルとマイグレーション), #1344, #1345, #1346, #1340 (物体検出によるクロップ矩形供給)
- **関連 ADR**: 0035 (Aggregate 単位 Repository), 0061 (画像登録の統一エントリと pHash 分類), 0083 (タグ欄の TagPanelWidget 切り出し)

## Context

#1339 は「画像の一部を切り出して新しい画像として扱う」機能を求めている。データ層の要件は次の 3 点。

- 切り出した画像が**どの画像のどの矩形から作られたか** (直接の親と切り出し位置) を保存する。
- 切り出した画像は通常の画像と同じ `images` テーブルへ**独立した ID** で登録する。アノテーション・
  スコア・エクスポートなど既存機能がそのまま効く必要があるため、専用の画像テーブルは作らない。
- 子を親としてさらに切り出す (再クロップ) を許す。運用上、登録した画像を削除しない前提で設計する。

一方、既存スキーマには「同一画像の派生」を表す `processed_images` (リサイズ・アップスケール等の
加工画像) がある。ここは `images.id` に従属し、**独立した画像 ID を持たない**。クロップ画像は
アノテーション対象として独立した画像であり、`processed_images` とは責務が異なる。

## Decision

### 1. 専用の関係テーブル `crop_relations` を追加する

`crop_relations` は次の列だけを持つ。

| 列 | 内容 |
| --- | --- |
| `id` | 関係行の PK |
| `parent_image_id` | 直接の親画像 (`images.id`, ON DELETE CASCADE) |
| `child_image_id` | 子 = クロップ画像 (`images.id`, ON DELETE CASCADE) |
| `x` / `y` / `width` / `height` | **直接の親画像基準**の切り出し矩形 (px) |
| `origin` | 切り出し由来の文字列。既定 `manual` |
| `created_at` | 作成時刻 |

制約は `UniqueConstraint("child_image_id")` (1 子 = 1 親) と
`Index("ix_crop_relations_parent_image_id")` (親からの子一覧引き)。

### 2. 直接の親だけを記録し、祖先は連鎖で表現する

親 → 子 → 孫は「親-子」「子-孫」の 2 行で表現する。祖先 ID や世代を非正規化して持たない。
座標も常に**直接の親基準**で保存し、祖先基準への変換は必要になった時点で連鎖を辿って計算する。
これにより再クロップが特別扱い不要になり、親側の画像サイズ変更に伴う座標の意味の揺れも起きない。

### 3. 由来は文字列カラム `origin` で持つ

手動の矩形選択は `manual`、将来の物体検出由来は検出器名等の文字列を入れる。列を文字列にして
おくことで、#1340 が追加マイグレーションなしに由来を記録できる。

### 4. ProcessedImage との整合

- クロップ画像は独立した `images` 行として登録され、**自身の `processed_images` 行を持つ**
  (通常画像と同じ登録経路・同じリサイズ加工を通る)。
- `processed_images` は「同一画像の加工版」、`crop_relations` は「別画像への切り出し」で責務が別。
  クロップの親子関係を `processed_images` に混ぜない。
- 既存テーブルの既存カラムは削除・改名しない。追加は `crop_relations` の新規作成のみ。

### 5. アクセスは Repository 経由 (ADR 0035)

`CropRelationRepository` (`add_relation` / `get_children` / `get_parent`) を追加し、
`ImageDatabaseManager` は `crop_relation_repo` を DI + 既定生成で保持する。
`add_relation` は子の二重登録・FK 違反を `IntegrityError` としてそのまま伝播させ、
「保存されていないのに成功扱い」になる経路を作らない。

## Alternatives and rationale

- **`images` に `parent_id` 列を足す**: 座標 4 列と由来 1 列も `images` に載ることになり、
  クロップでない画像 (大多数) では常に NULL になる。`images` は登録・検索の中心テーブルで
  参照箇所が多く、列追加の影響範囲が広い。却下。
- **`processed_images` を流用する**: `processed_images` は独立した画像 ID を持たない従属行で、
  「クロップ画像を通常画像として扱う」という要件と噛み合わない。加工版と切り出しの意味も混ざり、
  既存のリサイズ取得クエリが壊れる。却下。
- **汎用 `image_relations` (relation_type 列付き)**: 現時点で必要な関係はクロップ 1 種のみで、
  汎用化すると座標列が他の関係種別では無意味になる。YAGNI により却下。別種の関係が必要に
  なった時点で専用テーブルを追加する方が安い。

## Consequences

- クロップ画像は既存のアノテーション・検索・エクスポートをそのまま利用できる。
- 親からの子一覧、子からの親は 1 クエリで取得でき、再接続後も保持される。
- 祖先を辿るコストは世代数に比例する。世代は実運用で浅い想定のため許容する。
  深い連鎖の一括取得が必要になったら再帰 CTE か非正規化を別途検討する。
- 画像削除は運用前提として行わないが、FK は CASCADE のため親削除時に関係行も消える。
  切り出し出自を残す要件が出た場合は別途退避を設計する (本 ADR の対象外)。

## #1340 向け拡張点

- **矩形供給元の差し替え点**: `CropCreateRequest` (`src/lorairo/domain/crop_request.py`) を受ける
  サービス関数は、矩形の出所を知らない。GUI の矩形選択も物体検出も同じ request 型を組み立てて
  同じサービス関数へ渡す。これが差し替え点であり、検出器を足してもサービス層は変更不要。
- **`origin` カラムの用途**: 手動選択は `manual`、検出器由来は検出器名等の文字列を入れる。
  由来別の絞り込み・表示はこの列だけで足りる。
- **検出モデル名・信頼度**: `crop_relations` には足さない。検出実行のメタデータ (モデル名、
  信頼度、検出時刻など) は将来別テーブルで `crop_relations.id` を参照して持つ。関係テーブルを
  検出器の都合で膨らませない。
- **バッチ・部分失敗**: 1 枚の親から複数矩形をまとめて切り出す際の進捗・部分失敗の扱いは
  #1340 で設計する。本 ADR のデータ層は 1 件ずつの登録のみを規定する。
