# ADR 0039: Agent PR Maintenance Automation

## Context

LoRAIro では、Codex や Claude Code などのエージェントが Issue 対応や機能実装を行い、PR を作成する運用が増えている。PR 作成後は、CI、Bot によるコードレビュー、人間レビューの結果を確認し、必要に応じて修正コミットを追加したうえで、問題がなければスカッシュマージする必要がある。

現状では、この PR 作成後の保守ループを人間が以下の手順で手動実行している。

1. CI の完了を待つ。
2. CI の失敗ログを読む。
3. コードレビューのコメントを読む。
4. エージェントへ修正を指示する。
5. 修正後に再度 CI とレビュー結果を確認する。
6. 問題がなければスカッシュマージする。

この手作業の多くは定型化できる。一方で、レビュー修正が連鎖する場合は、局所修正ではなく設計判断が必要になっている可能性がある。そのため、保守ループを自動化するにあたっては、修正ループの上限と設計エスカレーションの条件を明確に定める必要がある。

## Decision

### 1. PR を作成したエージェントが保守を継続する

PR を作成したエージェント自身が、同じセッションかつ同じ worktree で、CI とレビューが完了するまで保守ループを継続する。

- PR 作成後に別の監視役(watcher)へ即時委譲しない。
- ドラフト PR として作成した場合でも、ローカル検証済みでレビュー可能であれば、同じセッションで Ready for review へ切り替えてから保守ループを開始する。
- PR 作成時は、ユーザーが明示的にドラフトを求めた場合や、実装がまだレビュー不能な場合を除き、`--draft` を使用しない。
- PR 作成直後に `gh pr view "$PR" --json isDraft -q .isDraft` でドラフト状態を確認する。ドラフトであれば `gh pr ready "$PR"` を実行して再確認する。再確認後もドラフトのままであれば自動マージ設定へ進まず、明確なエラーとして停止する。
- ユーザーが明示的にドラフト維持を求めた場合、検証が未完了または失敗中の場合、あるいはスコープがレビュー可能でない場合に限り、ドラフトのまま停止して理由を報告する。
- `@codex fix` のような GitHub コメント駆動の修正コマンドは使用しない。
- 修正作業は、コンテナ内の Codex CLI または Claude Code CLI が既存の作業文脈を保持したまま実行する。
- 作業場所は、PR 作成に使用した専用の worktree をそのまま継続利用する。

この方針は、GitHub コメント経由で別タスクを起動する方式よりも、実装時の文脈を保持しやすい点を優先している。

### 2. CI とレビューの完了待ちはポーリングで行う

PR 作成後、エージェントは `gh` コマンドで PR の状態をポーリングする。

- 最大待機時間:20 分
- ポーリング間隔:3 分
- CI 状態、CI 失敗ログ、レビューコメントは `gh` および `gh api` で取得する。
- 20 分を超えても完了しない場合は、PR コメントで状況を通知して一旦停止する。

想定する基本コマンドは以下のとおりである。

```bash
gh pr view "$PR" --json \
  number,title,isDraft,headRefName,headRefOid,baseRefName,mergeStateStatus,reviewDecision,statusCheckRollup,labels

gh pr checks "$PR" --json name,state,bucket,link,startedAt,completedAt,workflow

gh run view "$RUN_ID" --log-failed
```

レビューコメントの取得には、必要に応じて REST API と GraphQL API を併用する。ただし、レビュースレッドの自動解決(resolve)は行わない。

### 3. 修正ループの上限

CI の失敗またはレビューコメントがある場合は、同じ worktree で修正を行う。既存運用と同様にテスト、Ruff、mypy などの検証を完了させてからコミットおよびプッシュする。

- 修正ループは最大 4 回まで許可する。
- 4 回目の修正でも CI またはレビュー上の問題が解消しない場合は、自動修正を停止する。
- レビューコメントへの対応後に追加の指摘が連鎖する場合は、設計自体に問題がある可能性として扱う。

### 4. レビューコメントへの返信

すべてのレビューコメントに対して日本語で返信する。

- 修正した場合は、修正内容、コミット、検証結果を簡潔に返信する。
- 修正しない場合は、対応不要と判断した理由を明記して返信する。
- レビュースレッドの自動 resolve は行わない。

### 5. 自動マージの条件

以下の条件をすべて満たす場合、人間を介さずにスカッシュマージを実行する。

- Bot レビューでマージを妨げる(blocking な)問題が残っていない。
- CI および必須チェック(required checks)がすべて成功している。
- PR がドラフトではない。
- PR 作成直後の非ドラフト確認(no-draft postcondition)が成功している。
- マージ対象の head SHA が確認済みの SHA と一致している。
- 自動修正ループが上限に達していない。
- 設計エスカレーション状態ではない。

マージ方式はスカッシュマージに統一する。

```bash
gh pr merge "$PR" --squash --auto --delete-branch --match-head-commit "$HEAD_SHA"
```

### 6. 設計エスカレーション

以下のいずれかに該当する場合、エージェントは自動修正を停止し、設計変更の検討としてエスカレーションする。

- 4 回目の修正でも CI またはレビュー上の問題が解消しない。
- 同じ責務境界や同じファイル群でレビュー指摘が連鎖する。
- 局所修正ではなく、パブリック API、ワーカーライフサイクル、GUI の Signal/Slot 構造などの設計判断が必要になった。
- ワークフロー、権限、シークレット、main ブランチへの直接プッシュ、履歴改変、大規模な設計変更が必要になった。

エスカレーション時は、以下の 3 つを実施する。

1. PR に現状と設計上の選択肢を日本語でコメントする。
2. 設計検討用の Issue を作成する。
3. PR と Issue の双方に設計検討用ラベルを付与する。

### 7. 許可操作と禁止操作

自動修正で許可する操作:

- アプリケーションコードの修正
- テストの追加および修正
- ドキュメントの更新
- DB マイグレーションの追加および修正
- 依存関係およびロックファイルの更新

自動修正で禁止する操作:

- `.github/workflows/**` の変更
- GitHub Actions の権限変更
- シークレットおよび環境変数設定の変更
- `main`(デフォルトブランチ)への直接プッシュ
- Git 履歴の改変
- 大規模な設計変更

禁止操作が必要になった場合は、実装せず設計エスカレーションへ切り替える。

### 8. 状態管理

当面、状態の永続化は行わない。

- ループ回数と確認済み head SHA は、同一エージェントセッション内のメモリで管理する。
- セッションが中断した場合は、人間が手動で再指示する。
- 将来、長時間運用や復旧性が必要になった場合は、PR コメント内の HTML マーカー等による状態永続化を追加する。

## Rationale

### 同一エージェントが保守を継続する理由

PR 作成直後のエージェントは、設計意図、変更理由、実施済みの検証内容を最も詳しく把握している。GitHub コメントから新しいクラウドタスクを起動する方式は文脈が薄くなりやすいため、修正精度より制御の単純さを優先する場面を除き採用しない。

### ポーリングを採用する理由

LoRAIro の通常の CI と Bot レビュー待ちは 20 分を超えることが稀である。Webhook 監視サービスや常駐デーモンを先に導入するよりも、PR 作成エージェントが `gh` で短時間ポーリングする方が実装も運用も単純である。

### 修正上限を 4 回とする理由

CI の失敗は、一時的な環境差や軽微なテスト漏れにより複数回の修正を要することがある。一方で 4 回修正しても解消しない場合、局所修正を積み重ねるより設計変更の検討へ切り替える方が安全である。

### レビュースレッドを自動 resolve しない理由

返信自体は自動化してよいが、解決済み扱いにする判断はレビューの意味論に関わる。自動 resolve はレビュアーの確認を省略したように見える恐れがあるため、初期運用では返信のみにとどめる。

## Consequences

### 良い点

- PR 作成後の CI 確認、レビュー確認、修正指示、再確認、マージに伴う手作業を削減できる。
- PR 作成エージェントの実装文脈を保ったまま修正できる。
- 4 回の上限と設計エスカレーションにより、局所修正の無限ループを防止できる。
- `gh` を GitHub I/O の境界とすることで、LLM に未整理の GitHub 状態を直接探索させずに済む。

### 悪い点

- PR 作成エージェントのセッションが、CI とレビューの完了まで最大 20 分間占有される。
- セッションが落ちた場合は自動復旧せず、人間の再指示が必要となる。
- ポーリング方式のため、長時間の CI や遅延レビューが増えた場合は、別監視役や GitHub Actions への移行が必要になる。
- 人間を介さないマージの安全性は、必須チェックと Bot レビューの品質に強く依存する。
