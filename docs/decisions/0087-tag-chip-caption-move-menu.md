# ADR 0087: タグチップ右クリックをキャプション移動の操作ハブにする

## Context

再取り込みした学習データセットの `.txt` タグ欄には、タグではなくキャプションとして扱うべき文章的な文字列が混入することがある。

既存のタグチップは翻訳がない項目を点線スタイルで表示できる。さらに、右クリックメニューから翻訳・種別・使用頻度・精査(refinement)の各操作へ進めるため、ユーザーが目視で判断する入口としてすでに機能している。

## Decision

未一致の長文を対象とした隔離キューや自動降格判定は新設しない。既存のタグチップ右クリックメニューを操作ハブとして拡張する。

- **「別のタグに置換…」**: 入力ダイアログで置換先を受け取り、既存の `tag_replace_requested(from, to)` と `replace_tag_for_images_batch` の経路へ流す。
- **「キャプションに移動」**: 現在表示中のキャプション投影文字列の末尾へ `, ` 区切りでタグ文字列を追記し、既存の `ImageDBWriteService.update_caption` で新しいキャプション行として保存する。
- **移動元タグの論理却下(soft-reject)**: キャプションの保存が成功した場合に限り、移動元タグを `reject_reason='incorrect'` で論理却下する。

## Rationale

タグ欄への文章混入は少数にとどまる。人間がその場で「置換」「キャプションへ移動」「削除」「種別変更」を選べれば十分である。仕分け専用の UI を新設するとデータ分類ルールや保存先契約が増える一方、既存のタグチップには翻訳なし表示とタグ単位の操作文脈がすでに揃っている。

キャプションテーブル自体は複数行を保持できるが、現行の UI とエクスポートは最新の投影済みキャプション文字列を扱う。そのため移動時には呼び出し側で現在のキャプションとタグ文字列を結合し、保存 API には完成済みの文字列を渡す。

## Consequences

キャプション側はチップ化されていないため、今回の移動はタグからキャプションへの片方向のみとする。将来キャプションの複数表示 UI が導入された場合は、キャプション側の項目単位の操作として逆方向の移動を追加できる。

## Implementation Notes

本決定は Issue #1240 および PR #1285 で実装した。

- 右クリックメニューへ新規追加した操作は「別のタグに置換…」と「キャプションに移動」の 2 項目のみである。
- 削除操作は新規メニュー項目として追加せず、既存のタグチップの `×` ボタンとクリックによる論理却下(soft-reject)の導線を用いる。
- キャプションへの結合区切りは `, ` とする。結合済みキャプションを先に保存し、保存成功時のみ移動元タグを論理却下することで、保存失敗時にタグだけが失われる事態を防ぐ。
