# ADR 0019: Export Filter Required Design

## Context

`lorairo-cli export create` コマンドの設計が、LoRAIro 本来の目的と乖離していた。

### 現状の課題

1. **本来の目的**
   - LoRAIro の `export` 機能は、**LoRA 学習用データセットの作成**を目的としている。
   - 学習データセットは、特定タグ・高評価・特定レーティングなど「特定条件を満たす画像群」で構成される。
   - データベースの全画像をそのまま出力する「全件エクスポート」は、学習用途として現実的に存在しない。

2. **現状の実装**
   - `src/lorairo/cli/commands/export.py:95` が `repository.get_images_by_filter()` を引数なしで呼び出している。
   - その結果、フィルタ条件を明示しないと DB 内の全画像(例:21,029 件)が取得される。
   - Issue #166 では「指定プロジェクトの 9 件だけのはずが、21,029 件を処理してハングアップした」と報告された。

3. **設計方針の歪み**
   - 当初は「プロジェクトフィルタを後から追加する」という方針が検討されていた(Issue #166 原文の「対応方針(案)」)。
   - しかしこの方針では「フィルタなし=全件取得」という挙動を正常ケースとして残してしまう。
   - 大量データの誤エクスポートを構造的に防ぐことができない。

## Decision

**`export create` コマンドではフィルタ条件を必須とし、フィルタなしの呼び出しはエラーとして拒否する。**

### 具体的変更

1. `export create` の CLI 引数に以下のフィルタオプションを追加する。
   - `--project PROJECT`
   - `--tags "tag1,tag2"` / `--excluded-tags`
   - `--caption "..."`
   - `--manual-rating {PG|R|X|XXX}` / `--ai-rating {...}`
   - `--include-nsfw`
   - `--score-min FLOAT` / `--score-max FLOAT`

2. `src/lorairo/cli/commands/export.py:95` の引数なし `repository.get_images_by_filter()` 呼び出しを削除する。

3. 入力バリデーションを追加する。
   - 上記フィルタが 1 つも指定されていない場合は、`exit_code=2` とエラーメッセージを返して終了する。
   - エラーメッセージ例:`"エクスポートには最低1つのフィルタ条件が必要です。例: --project foo --tags cat"`

4. `ExportCriteria`(`src/lorairo/api/types.py`)に `has_any_filter()` メソッドを追加する。

```python
class ExportCriteria(BaseModel):
    # ... 既存フィールド ...
    
    def has_any_filter(self) -> bool:
        """フィルタ条件が1つ以上指定されているか検証。"""
```

5. GUI 側は既存の「選択状態からエクスポート」経路を維持する。`SelectionStateService.get_current_selected_images()` により最低 1 枚の選択が保証されているため、実質的にフィルタ条件として機能する。

## Rationale

### 検討した選択肢

| 選択肢 | 概要 | 採否 |
|-------|------|------|
| A:フィルタ必須化(エラー化) | フィルタなしの呼び出しを `exit_code=2` で終了させる | **採用** |
| B:警告と確認プロンプト | `"全件エクスポートしますか? (y/N)"` で確認する | 却下 |
| C:ドライラン強制 | 件数表示のみ行い、実処理には `--execute` を必須にする | 却下 |
| D:全件エクスポート許可(現状維持とバグ修正のみ) | 当初 Issue の方針を踏襲する | 却下 |

### A を採用した理由

- **LoRA 学習目的との整合性**:学習用途で全件エクスポートが必要な場面は想定できず、フィルタ必須化が設計思想に沿っている。
- **構造的な誤操作防止**:21,029 件の全件取得のような事故を設計レベルで防げる。
- **シンプルさと一貫性**:ルールに例外がなく、ユーザーが理解しやすい。
- **自動化スクリプトとの親和性**:対話入力が不要であり、設定ミスを即座に検知できる。

### B (確認プロンプト) を却下した理由

- CI/CD や cron などの非対話環境で利用できない。
- 自動化スクリプトが `stdin` 待ちで停止してしまう。
- LoRA 学習用途で「本当に全件出力するか」を尋ねる必要性がない。

### C (ドライラン強制) を却下した理由

- 常に 2 回のコマンド実行が必要となり、操作性が低下する。
- `--execute` フラグが必須になるだけで、本質的には選択肢 B と同じ課題が残る。
- フィルタ必須化の方がシンプルに目的を達成できる。

### D (現状維持) を却下した理由

- 引数なし `get_images_by_filter()` を呼び出せる構造を残してしまい、全件取得バグの根本原因が解消されない。
- ユーザーが意図せず 21,029 件をエクスポートする事故が再発し得る。
- LoRAIro の用途として不自然な挙動である。

## Consequences

### 良い点

- LoRA 学習目的に沿った一貫した動作になる。
- 大量データの誤エクスポートを構造的に防止できる。
- CLI 引数からエクスポートの意図が常に読み取れるようになり、スクリプトの可読性が向上する。
- GUI 側は選択状態が実質的なフィルタとして機能するため、変更が不要である。

### トレードオフ

- 既存スクリプトが `export create --project foo --output /tmp/out` のような形で利用されていた場合、破壊的変更により動作しなくなる可能性がある。
- `--help` に表示されるフィルタオプションが増え、出力がやや長くなる。
- 初回利用者にとっては、なぜエラーになったのか戸惑う可能性がある。

### 軽減策

- **エラーメッセージに移行ガイドを表示する**:
  ```
  Error: エクスポートには最低1つのフィルタ条件が必要です
  例: lorairo-cli export create --project foo --tags cat --output /tmp/out
  詳細: lorairo-cli export create --help
  ```
- **CHANGELOG に破壊的変更を明記する**:migration セクションに「フィルタ条件必須化」を記載する。
- **`--help` の出力を整理する**:Typer のヘルプグループ機能を使い、フィルタオプションをグループ化して視認性を確保する。
