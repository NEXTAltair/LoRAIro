# ADR 0095: Clef アノテーション確認の固定対象バッチと画像別結果保持

## Context

ADR 0094 の初期実装は選択画像の一時的な警告に対応した。画像を切り替えると結果が消え、
複数画像の結果を見ながら手動修正する作業には向かなかった。
ユーザーは開始時に対象を固定したバックグラウンド処理、画像ごとの結果保持、
結果画面の警告から手動確認へ進む導線を求めている。画面上の呼称は「アノテーション確認」とする。

## Decision

- 既存のステージング集合、WorkerManager、Clef service、結果タブ、検索画面の手動編集を再利用する。
  新しい通信ライブラリや別の生成モデル経路は追加しない。
- 明示操作で開始時の対象画像 ID を順序付きの不変集合として取り込む。最大 500 枚とし、
  バックグラウンドで全対象の snapshot を読み取ってから API 呼び出しを開始する。
  選択・ステージングの変更で実行対象は変えない。
- 画像ごとの最新結果を専用 Repository と追加テーブルに保存する。注釈 ID・原文・確率・状態、
  fingerprint、モデル、警告基準、確認時刻を保持し、再起動後も読み出せる。
  保存と通知は画像ごとに行い、中止後も完了済みの結果を保持する。
  単画像とバッチの並行実行では、確認開始時刻を比較する原子的 upsert で、遅れて完了した
  古い処理が新しい処理の保存結果を上書きすることを防ぐ。
- 原画像・注釈の fingerprint と判定モデル・基準が一致しない保存結果は古い結果として表示する。
  履歴の内容は保持するが、古い一致確率を現在の注釈への判定として表示しない。
- 結果タブで画像ごとの警告・失敗・未評価を表示し、対象画像を検索画面の既存手動編集で開く。
  一覧は DB から直近 500 枚を取得し、古い結果かどうかの確認も worker で行う。
  それ以前の保存結果は画像の詳細欄から個別に参照できる。
  警告を理由に注釈や reviewed 状態を自動変更しない。
- GUI の結果保存は明示した確認処理に属する。CLI の既存読み取り専用実行は保存を行わない。

## Rationale

既存の選択・ステージング状態はユーザー操作で変化するため、実行対象の不変コピーを分ける。
API 送信の前に内容を読み取ることで、待機中の変更も fingerprint による無効化の対象になる。
画像ごとの保存は、中止や失敗を理由に他画像の完了結果を失うことを防ぐ。
専用テーブルはタグ confidence や品質スコアと確認結果を混同せず、既存の手動編集を使える。

## Consequences

追加テーブルの Alembic マイグレーションが必要となる。
保持するのは画像ごとの最新結果で、全実行履歴や自動再試行は導入しない。
送信済み HTTP は設定したタイムアウトまで終了を待つ場合がある。
警告がなくても内容の正確さを保証せず、修正の判断はユーザーが行う。
