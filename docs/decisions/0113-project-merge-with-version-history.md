# ADR 0113: 複数プロジェクトを画像・タグ・データセットの版履歴ごと統合する

## Context

プロジェクトごとに分けて作った画像・タグ・データセットの版を、1 つのプロジェクトへまとめたいという要求がある(Issue #1660)。ADR 0112 で、別プロジェクトの画像を読み取り専用で開いてコピーし、由来を記録する仕組み(`ProjectTransferService.stage_images`、`image_origins`、`dataset_version_origins`、`project_transfer_runs`)を入れた。統合はこれを、プロジェクト全体と版の履歴へ広げる処理になる。

統合では、複数の統合元が同じ画像・同じ名前のデータセットや版を持つことがある。名前を自動で付け替えると、利用者が後で版を探せなくなり、学習の再現に使う名前も変わる。

## Decision

### 1. 統合元の全体を統合先へコピーし、統合元は変更しない

統合元(1 つ以上)の画像・アノテーション・生成メタデータ・データセット・版(フォルダ・画像の所属・学習テキスト)・学習設定を、統合先へコピーする。統合先は既存のプロジェクトでも、新しく作るプロジェクトでもよい。統合元は ADR 0112 と同じく読み取り専用で開き、DB も画像ファイルも書き換えない。統合先が統合元のどれかと同じとき、統合元が重複するときは拒否する。

画像は統合元ごとに `ProjectTransferService.stage_images` で統合先のセッションへ足す。`project_transfer_runs` は統合元ごとに 1 行で、種類は `merge_project` にする。

### 2. 同じ画像は 1 枚にまとめる

同じ画像(ADR 0061 の DUPLICATE。統合先に既にある画像と、同じ実行で先に取り込んだ統合元の画像を含む)は 1 枚にまとめる。タグ・アノテーションは ADR 0112 の規則で和集合にする(タグは `(モデル, タグ)`、キャプション・スコア・スコアラベル・レーティングは値と `created_at` で重複を除き、時点の違う同じ値の記録は残す)。由来は統合元ごとに `image_origins` に残す。統合元の順番(指定順)で、先の統合元の画像をまとめ先にする。各版の画像の所属は、まとめた 1 枚を指す。

### 3. 版は親子の連なりごと複製し、由来を記録する

統合元の版は、統合元の版 ID の順に統合先へ作り、parent を統合先の ID に付け替える。作業中の版(`is_working=True`)は作業中のまま引き継ぐ。版ごとに `dataset_version_origins` へ、統合元のプロジェクト名・データセット名・版 ID・版名と、取り込んだ操作(`transfer_run_id`)を記録する。版の対応は `DatasetRepository.list_version_origins` で統合先から読む。

学習設定(`training_configs`)はデータセットと版の ID を付け替えて複製する。統合の最後に、足したデータセットごとに `KOHYA_DATASET` のタグを最新版へ同期する(ADR 0104)。

### 4. 名前の衝突は計画に示し、利用者が対応を指定するまで確定しない

統合先のデータセット名は、指定が無ければ統合元と同じにする。次の場合を衝突とする。

- `dataset_name`: 複数の統合元のデータセットが、履歴をまとめる指定なしに同じ名前になる
- `dataset_exists`: 統合先に同じ名前のデータセットが既にある(履歴をまとめる指定がない)
- `version_name`: 1 つのデータセットの中で、同じ名前の版が 2 つ以上になる
- `multiple_working_versions`: 1 つのデータセットの中で、作業中の版が 2 つ以上になる(ADR 0098 の「データセットごとに作業中の版は 1 つまで」を守る)

衝突は自動で解消しない。利用者が名前の対応(`MergeMapping`)で、データセットの名前の付け替え、版の名前の付け替え、履歴をまとめる指定のいずれかをする。存在しない統合元・データセット・版を指す対応と、互いに矛盾する対応は不正な指定として拒否する。データセットの名前が衝突している間は、そのデータセットの版の衝突は判定しない(データセットの対応を決めてから判定する)。

### 5. 履歴をまとめる指定

同じデータセットの版を 1 つの履歴にまとめる指定では、統合元のデータセットを利用者が指定した順に連ねる。前の要素の最新版を、次の要素の最初の版の parent にする。

- 最新版は `DatasetRepository._latest_version_ids` と同じ規則(確定済みの版のうち、他の確定済みの版の parent に指されていない版で ID が最大のもの)で決める
- 最初の版は、同じデータセットに parent が無い版のうち ID が最小のもの。parent を付けるのはこの 1 つだけで、ほかの根の版はそのままにする
- 統合先に同じ名前のデータセットが既にあれば、その履歴を先頭にする(既存のデータセットへ続けて足す)
- 確定済みの版が無い要素は飛ばし、その前の要素の最新版を次の要素に渡す

版は履歴の順に作るので、まとめた後の最新版は最後の要素の最新版になる。

### 6. 既定は計画で、確定には `--confirm` が要る

計画は、統合先のセッションで画像の取り込みまで同じ判定を行ってから rollback し、ファイルを一切書かない。新しく作る統合先への計画は、一時ディレクトリに空のプロジェクト DB を作って行い、終わったら消す。計画は、取り込む画像数(統合元ごとの複製・まとめる枚数)、ハッシュ一致でまとめる画像、版の対応(統合先の名前・parent)、未解決の衝突を示す。名前の対応のひな形(`mapping_template`)を出し、利用者はこれを書き換えて mapping ファイルにできる。

衝突が残ったまま確定しようとしたら、何も書かずに拒否する(`UnresolvedMergeConflictError`)。

### 7. 統合先は 1 セッション 1 commit、ファイルは staging から移す

ADR 0112 と同じく、統合先への書き込みは 1 つのセッションで行い、最後に 1 回だけ commit する。全統合元のファイルを `image_dataset/.transfer_staging/<実行ごと>/<統合元ごと>/` に置いてから最終パスへ移し、その後に commit する。途中で例外が起きたら rollback し、移したファイルと作ったディレクトリ、staging を削除する。新しく作った統合先は、統合が失敗したら削除する。

### 8. CLI

- `project merge SRC... --into DST [--create] [--map-dataset SRC:DS=NEW] [--map-version SRC:DS/VER=NEW] [--join-dataset NEW=SRC1:DS,SRC2:DS] [--mapping-file m.json] [--dry-run | --confirm]`: `--confirm` が無ければ計画だけを出す。`--into` は `--project` / `-p` と同じ。`--create` は統合先を新しく作る(既にあれば拒否)。mapping ファイルは `mapping_template` と同じ形で、`--map-*` / `--join-*` の指定が優先する
- `project merge-show -p DST`: 統合先の版ごとの由来(統合元のプロジェクト・データセット・版 ID・版名)

名前に `:`・`/`・`=` を含むデータセット・版は、CLI の短い指定では表せないので mapping ファイルで指定する。

## Constraints

- 統合元の DB は schema が head であること(ADR 0112 と同じ。古い DB は開かない)
- 統合元の全画像とデータセットを 1 回でメモリに読む。統合元が非常に大きい場合の分割は行わない
- 2 つの統合元の画像が統合先の同じパスになる場合(統合元のディレクトリ名とファイル名が一致する場合)は拒否する

## Consequences

- 統合元の画像・注釈・版が統合先に複製されるため、ディスク使用量は増えるが、統合元はそのまま残る
- 同じ名前のデータセット・版を持つ統合元は、名前の対応を指定するまで統合できない(意図しない名前の付け替えは起きない)
- 履歴をまとめると、統合元で最新版だった版の `KOHYA_DATASET` のタグは、まとめた後の最新版の内容へ同期される(ADR 0104)
- 統合を再実行すると、画像は由来が記録済みとして重ねず、データセットは同名の衝突として止まる
