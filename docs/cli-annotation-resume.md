# アノテーション実行の再開

`annotate run --run-id ID` は実行対象と画像ごとの進捗をプロジェクト内へ保存する。
中断後は同じプロジェクト、モデル、設定で `--resume ID` を指定すると、まだ開始していない
画像だけを処理する。通常の `annotate run` は従来どおり動作し、実行記録は作成しない。

```powershell
lorairo-cli --json annotate run --project my_project --model openai/gpt-4o --image-ids-file ids.txt --resolution 1024 --run-id captions_20261103
lorairo-cli --json annotate run --project my_project --model openai/gpt-4o --resume captions_20261103
```

複数モデルの場合は、開始時と同じモデルを同じ順序で指定する。`--model` は再開時も必須。
`--run-id` と `--resume` は排他的。ID は先頭が英数字の ASCII 英数字・`_`・`-`、1〜64文字。
既存のIDは上書きしない。状態は `<project>/.lorairo/annotation-runs/<ID>.sqlite3` に置く。
隣接する `<ID>.lock.sqlite3` のSQLiteロックにより、同一実行の同時起動を拒否する。
クラッシュ後はOSがロックを解放するため、ロックファイルを削除して復旧する必要はない。

初回の選択は通常のフィルタ、ID選択、ID昇順、offset、limit、resolutionの規則を使う。
再開時は保存した対象と解像度を使い、`--unrated` / `--missing-model` を再評価しない。
`--image-id`、`--image-ids-file`、`--unrated`、`--missing-model`、非ゼロの`--offset`、
`--limit`、`--resolution` を `--resume` と併用すると入力エラーになる。
通常の500件上限、IDファイルの100,000件上限、元画像への直接アノテーション禁止は維持する。
実行記録を使う場合は1画像ずつ処理するため、`--batch-size` は実行単位を変更しない。

## 状態と再送の扱い

| 状態 | 意味 | `--resume` |
| --- | --- | --- |
| `pending` | まだ処理を開始していない | 実行する |
| `in_flight` | 処理開始を永続化済みで、終了を確認できていない | 再送しない |
| `completed` | 要求した全モデルの成功結果とDB保存を確認済み | 再送しない |
| `failed` | ロード、モデル結果、保存、moderation等の失敗を確認済み | 再送しない |
| `skipped` | 解像度不一致、moderationによる除外等 | 再送しない |

`in_flight` はmoderationを含む外部呼び出しより前にSQLiteへコミットする。
タイムアウト、Ctrl+C、プロセス停止、結果受信後やDBコミット直後の停止では、その画像が
実際に処理されたか不明な場合がある。この状態を `pending` に戻す自動処理はない。
残りの `pending` は別の再開で続行できるが、曖昧な画像は引き続き `in_flight` と表示する。
停止が送信の直前だった場合も、保守的に `in_flight` のままとする。

これはプロバイダ側の exactly-once 保証ではない。送信とプロジェクトDB・実行記録のコミットを
一つのトランザクションにはできず、image-annotator-libのHTTP通信・出力検証や
プロバイダSDK内部の再試行にも影響しない（公開APIに無効化オプションがない）。
LoRAIroのmoderationバッチ失敗後の個別再送は、実行記録を使う場合だけ無効にする。
`failed` / `in_flight` の再試行が必要な場合は、プロバイダの利用記録と保存済みアノテーションを
確認し、対象IDを明示した**別の実行ID**で開始する。その操作には再送・追加費用の可能性がある。
実行記録を手で `pending` に書き換えない。モデルの一部だけが成功した画像も自動再試行しない。

## 再開前の検証

外部呼び出しの前に次を照合し、不一致なら処理を開始しない。

- プロジェクト名、DBの絶対パスとファイル識別子（device/inode）。コピーや別DBへの置換は拒否する。
- 正規化済みモデルIDのリストと順序。
- アプリケーション設定、および選択モデルと暗黙moderationモデルの設定のSHA-256。
- 固定した全画像のID、UUID、pHash、保存パス、実際に使用する画像の絶対パスと内容のSHA-256。

画像は実行直前にも再確認する。開始・再開時には対象画像をすべて読み取ってハッシュするため、
大量画像では開始前のI/Oが増える。各画像の推論メモリは1画像分に抑える。
APIキー、トークン、パスワード等の資格情報フィールドは設定ハッシュから除外するので、
キーの更新だけなら再開できる。設定の生値やプロンプトは実行記録に保存しない。
資格情報以外のアプリ設定も保守的に照合するため、推論と無関係な設定変更でも拒否し得る。
不一致時は元の設定・画像・DBへ戻してから再開する。初期化途中で失敗した不完全な記録を
自動上書きすることはない。新しい実行IDを使う前に、その実行で送信が始まっていないことを確認する。

ファイル識別子とSQLiteロックが正しく機能する同一マシンのローカルファイルシステムを前提とする。
実行中の画像・設定・モデルファイルの同時変更には対応しない。モデルIDが示すリモートモデルや
ローカル重み自体の変更までは検証せず、別の実行IDや通常実行との重複も自動検出しない。
状態ファイルの削除・巻き戻し・手動改変や、DBを同じファイルへ上書き復元した場合の整合性を保証しない。

## JSONと終了コード

`annotation_outcome` は保存した全対象を1件ずつ返す。`status` は上記5状態、`saved` は
この実行記録でDB保存を確認できたかを表す。以前の実行で完了した画像も結果に含まれる。
通常実行で使う `unexecuted` の代わりに、実行記録では `pending` を使用する。

最終 `result` の `run_id`、`resumed`、`state_path`、`pending`、`in_flight` は実行記録を
使用する場合だけ出力する。`total`、`completed`、`errors`（`failed`件数）、`skipped`、
`annotated`（保存確認件数）は実行全体の累積値。`unexecuted` は `pending` と同じ件数。
`loaded` と `results` は今回のコマンド呼び出しで読み込んだ画像数と得られた結果数。
`in_flight` は `errors` に含めず独立して報告する。現在の呼び出しが中断された場合は
`interrupted=true` とし、失敗理由には例外の種類を表示する。

| 終了コード | `status` | 意味 |
| --- | --- | --- |
| 0 | `success` | 処理対象が完了または正常に除外された |
| 3 | `partial_success` | 保存を確認できた結果があり、失敗・未処理・曖昧な画像も残る |
| 1 | `failed` | 保存を確認できた結果がなく、失敗・未処理・曖昧な画像が残る |
| 2 | `error` 行 | 不正なオプション、実行ID、再開条件の不一致等 |

全件が指定解像度に存在しない場合も失敗扱い。完了済み実行の再開は送信を行わず0で終了する。
未解決の `failed` / `in_flight` が残る実行では、再開で送信が0件でも終了コードは非ゼロのまま。
ロックやI/Oなど実行時のエラーは既存の構造化エラー契約に従う。

通常の `annotate run`（ID指定・ストリーミング）と `annotate import-batch` も、部分成功は3、
全体失敗は1、成功は0を返す。入力エラーは従来どおり2。
