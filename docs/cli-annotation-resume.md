# アノテーション実行の再開

`annotate run --run-id ID` を指定すると、実行対象と画像ごとの進捗をプロジェクト内に保存します。処理が中断された場合は、同じプロジェクト・モデル・設定で `--resume ID` を指定することで、まだ開始していない画像だけを処理できます。

なお、通常の `annotate run` は従来どおり動作し、実行記録は作成しません。

```powershell
lorairo-cli --json annotate run --project my_project --model openai/gpt-4o --image-ids-file ids.txt --resolution 1024 --run-id captions_20261103
lorairo-cli --json annotate run --project my_project --model openai/gpt-4o --resume captions_20261103
```

## 実行 ID と再開時の指定ルール

- **複数モデルの指定**: 開始時と同じモデルを同じ順序で指定します。`--model` は再開時も必須です。
- **排他オプション**: `--run-id` と `--resume` は同時に指定できません。
- **ID の形式**: 先頭が英数字の ASCII 英数字・`_`・`-` で構成し、長さは 1〜64 文字とします。既存の ID は上書きしません。
- **状態ファイルとロック**: 状態は `<project>/.lorairo/annotation-runs/<ID>.sqlite3` に保存します。隣接する `<ID>.lock.sqlite3` の SQLite ロックにより、同一実行の同時起動を拒否します。クラッシュ後は OS がロックを解放するため、ロックファイルを手動で削除する必要はありません。

### 対象選択と併用できないオプション

初回の対象選択には、通常のフィルタ・ID 選択・ID 昇順・offset・limit・resolution の規則を使います。再開時は保存済みの対象と解像度をそのまま使うため、`--unrated` や `--missing-model` の再評価は行いません。

以下のオプションは `--resume` と併用できません。指定すると入力エラーになります。

- `--image-id`、`--image-ids-file`
- `--unrated`、`--missing-model`
- 非ゼロの `--offset`、`--limit`、`--resolution`

また、以下の既存制限と挙動も維持されます。

- 通常の 500 件上限、ID ファイルの 100,000 件上限、元画像への直接アノテーション禁止は維持します。
- 実行記録を使う場合は 1 画像ずつ処理するため、`--batch-size` を指定しても実行単位は変わりません。

## 状態と再送の扱い

| 状態 | 意味 | `--resume` 時の扱い |
| --- | --- | --- |
| `pending` | まだ処理を開始していない | 実行する |
| `in_flight` | 処理開始を永続化済みで、終了を確認できていない | 再送しない |
| `completed` | 要求した全モデルの成功結果と DB 保存を確認済み | 再送しない |
| `failed` | ロード、モデル結果、保存、moderation などの失敗を確認済み | 再送しない |
| `skipped` | 解像度不一致、moderation による除外など | 再送しない |

### `in_flight` の扱い

`in_flight` は moderation を含む外部呼び出しより前に SQLite へコミットします。タイムアウトや Ctrl+C、プロセス停止、結果受信後や DB コミット直後の停止が起きると、その画像が実際に処理されたか不明な状態になることがあります。

この状態を `pending` に自動で戻す処理はありません。残りの `pending` は別の再開で続行できますが、曖昧な画像は引き続き `in_flight` と表示します。送信の直前で停止した場合も、安全側へ倒して `in_flight` のままとします。

### 再送に関する制約と手動再試行

この仕組みはプロバイダ側の exactly-once 保証ではありません。外部送信とプロジェクト DB・実行記録のコミットは 1 つのトランザクションにまとめられないためです。また、`image-annotator-lib` の HTTP 通信・出力検証や、プロバイダ SDK 内部の再試行には影響しません(公開 API に無効化オプションがないためです)。

一方で、LoRAIro の moderation バッチ失敗後の個別再送については、実行記録を使う場合のみ無効にします。

`failed` または `in_flight` の画像を再試行したい場合は、以下の手順で進めてください。

1. プロバイダの利用記録と保存済みアノテーションを確認します。
2. 対象 ID を明示し、**別の実行 ID** で新しく実行を開始します(この操作には再送や追加費用の可能性があります)。

実行記録を手動で `pending` に書き換えないでください。また、モデルの一部だけが成功した画像も自動再試行は行いません。

## 再開前の検証

再開時は外部呼び出しを行う前に、以下の項目を照合します。不一致がある場合は処理を開始しません。

- プロジェクト名、DB の絶対パスとファイル識別子(device および inode)。コピーや別 DB への置換は拒否します。
- 正規化済みモデル ID のリストと順序。
- アプリケーション設定、および選択モデルと暗黙 moderation モデルの設定の SHA-256。
- 固定した全画像の ID、UUID、pHash、保存パス、実際に使用する画像の絶対パスと内容の SHA-256。

### 検証時のパフォーマンスと設定の扱い

画像は実行直前にも再確認します。開始時と再開時には対象画像をすべて読み取ってハッシュを計算するため、画像数が多い場合は開始前の I/O が増えます。なお、推論時のメモリ消費は 1 画像分に抑えます。

API キー・トークン・パスワードなどの資格情報フィールドは設定ハッシュから除外します。そのため、API キーの更新だけであればそのまま再開できます。設定の生値やプロンプトは実行記録に保存しません。

資格情報以外のアプリ設定は保守的に照合するため、推論と無関係な設定変更でも再開が拒否されることがあります。不一致が起きた場合は、元の設定・画像・DB へ戻してから再開してください。初期化途中で失敗した不完全な記録を自動上書きすることはありません。新しい実行 ID を使う前に、その実行で外部送信が始まっていないことを確認してください。

### 前提条件と保証範囲

- ファイル識別子と SQLite ロックが正しく機能する、同一マシンのローカルファイルシステムを前提とします。
- 実行中の画像・設定・モデルファイルの同時変更には対応しません。
- モデル ID が示すリモートモデルやローカル重み自体の変更までは検証しません。
- 別の実行 ID や通常実行との重複は自動検出しません。
- 状態ファイルの削除・巻き戻し・手動改変、および DB を同じファイルへ上書き復元した場合の整合性は保証しません。

## JSON 出力と終了コード

### イベント行と最終結果

`annotation_outcome` は保存した全対象を 1 件ずつ返します。`status` は上記の 5 状態を表し、`saved` はこの実行記録で DB 保存を確認できたかどうかを表します。以前の実行で完了した画像も結果に含まれます。なお、通常実行で使う `unexecuted` の代わりに、実行記録では `pending` を使用します。

最終の `result` 行では、以下のルールでフィールドを出力します。

- **実行記録使用時のみ出力**: `run_id`、`resumed`、`state_path`、`pending`、`in_flight`
- **実行全体の累積値**: `total`、`completed`、`errors`(`failed` 件数)、`skipped`、`annotated`(保存確認件数)
- **未実行件数**: `unexecuted` は `pending` と同じ件数
- **今回の呼び出し分**: `loaded`(読み込んだ画像数)、`results`(得られた結果数)

`in_flight` は `errors` に含めず、独立した項目として報告します。現在の呼び出しが中断された場合は `interrupted=true` とし、失敗理由には例外の種類を表示します。

### 終了コード一覧

| 終了コード | `status` | 意味 |
| --- | --- | --- |
| 0 | `success` | 処理対象が完了した、または正常に除外された |
| 3 | `partial_success` | 保存確認または正常な moderation 除外があり、失敗・未処理・曖昧な画像も残る |
| 1 | `failed` | 保存確認も正常な moderation 除外もなく、失敗・未処理・曖昧な画像が残る |
| 2 | `error` 行 | 不正なオプション、実行 ID、再開条件の不一致など |

### 判定の補足

- 全件が指定解像度に存在しない場合も失敗扱いになります。
- 完了済み実行を再開した場合は、外部送信を行わず終了コード 0 で終了します。
- 正常な moderation 除外とは、明示的なポリシー判断によるブロックを指します。moderation 自体の失敗、API キー不足、rating 未保存、解像度欠落、選択フィルタによる除外は部分成功の根拠に含めません。
- 未解決の `failed` や `in_flight` が残る実行では、再開時の送信が 0 件であっても終了コードは非ゼロのままになります。
- ロック競合や I/O などの実行時エラーは、既存の構造化エラー契約に従います。

なお、通常の `annotate run`(ID 指定・ストリーミング)と `annotate import-batch` でも、部分成功は 3、全体失敗は 1、成功は 0 を返します。入力エラーは従来どおり 2 です。
