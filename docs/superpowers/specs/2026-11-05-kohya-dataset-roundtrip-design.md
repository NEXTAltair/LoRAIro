# Kohya-ss 学習データセットの取り込みと書き出し (round trip) 設計

調査の経緯と実データの数値は Issue #1404 とそのコメントに残している。本書は、そこから決まった方針と、最初のプロジェクトの範囲をまとめる。

## 0. 用語

- **学習テキスト**: データセット側の、画像 × フォルダごとの `.txt` / `.caption` の中身。普段の画像のタグ (`Tag` テーブル) とは別物。「キャプション」は、文章のキャプションを入れる既存の `Caption` テーブルと紛らわしいため使わない。
- **要素**: 学習テキストの、カンマ区切りの 1 つ 1 つ。
- **トリガーワード**: 学習テキストの先頭に共通して付く要素。フォルダ名とは別物であり、フォルダ名から導かない。
- **データセット**: 複数のフォルダを持つ、学習プロジェクト全体。
- **版**: データセットの、ある時点の状態を固めたもの。

この用語は、設計書内の「タグ」という語が、普段の画像のタグを指すのか学習テキストを指すのかを区別するために置いた。この命名は私の判断で、ユーザーとは未合意。

## 1. 意図と理由

過去に Kohya-ss で学習に使ったデータセットを LoRAIro に取り込み、後から修正して出し直したい。
修正の頻度は、画像の差し替え・追加が最も多く、次にタグ修正である。

手動で整理されたタグは、各サイトから保存した画像とタグより精度と情報量が桁違いに高い。
また「何を学習させるためのデータセットか」という目的も明確である。
現状の取り込みは、これらを活かせていない。

- 画像と同名の `.txt` (タグ) と `.caption` (キャプション) しか読まない。
- フォルダ名 (`<繰り返し回数>_<名前>`)、学習設定 json、モデルのメタデータは読まない。
- 保存時のタグは、サイト保存のものも手動整理のものも同じ値 (`existing=True`, `is_edited_manually=False`, `model_id=None`, `confidence_score=None`) で入り、取り込み後に区別できない。
- 同じ画像 (pHash 一致) は重複として既存レコードに寄せられ、関連ファイルは既存レコードへ取り込まれる。複数フォルダに同じ画像がある場合、フォルダごとの別の学習テキストが 1 つの画像に混ざる可能性が高い (コードの記述から読み取った内容で、実際には未実行)。

## 2. ゴール

1. 取り込んだデータセットを、取り込み時と同じ形で書き出せる (round trip)。
2. 同じ画像を複数のフォルダに入れ、フォルダごとに別の学習テキストを持てる。
3. データセットは複数のフォルダを持つ。
4. データセットは版の履歴を持つ。版は、取り込み時点のフォルダ構成とタグの状態を固めたものである。
5. 取り込み時に、自動検出した候補を初期値として示し、ユーザーが確認して確定する。

## 3. スコープ

### 3.1 最初のプロジェクトに含める (決定済み)

1. データモデルと移行: データセット、版、フォルダ、画像 × フォルダごとの学習テキスト。Alembic のマイグレーションを含む。
2. 取り込み: ユーザー入力を伴う取り込みダイアログと、フォルダ構成・学習設定 json の読み取り。
3. 書き出し: 版を指定して、`<繰り返し回数>_<名前>` フォルダ + `.txt` の形で出力する。あわせて、sd-scripts 用の TOML (構成と学習パラメーター) を出力する (詳細は §9.5 と §12)。
4. 学習パラメーターの保存: 新しいテーブル `training_configs` (§9.5)。

### 3.2 後続 (最初のプロジェクトに含めない)

5. 編集と版の比較: フォルダへの画像の追加・差し替え、版間の差分表示。
   - 想定している使い方: 最新の版を元にした作業状態で編集し、確定して新しい版にする。この方式は私の案で、ユーザーとは未合意。

### 3.3 非ゴール

- タグ頻度 (`ss_tag_frequency`) の突き合わせによる、元フォルダの自動特定。
- ファイルの更新日時による、版の順序や元フォルダの判定。
- 学習の実行、LoRA 成果物の管理。
- 正則化画像 (調査したすべてのデータセットで存在しなかった)。

### 3.4 アンチゴール

- 生成サンプル画像 (`sample001/`) や作業用フォルダ (`終了/`, `__Processed/`) が、学習画像として取り込まれること。
- フォルダごとに別の学習テキストが、画像 1 つのタグ (画像直下の `Tag`) に混ざること。
- 自動検出の結果を、ユーザーの確認なしに確定すること。
- 既存のライブラリ機能 (検索、アノテーション、通常の画像登録) の挙動が変わること。

## 4. 決定事項 (ユーザーの決定)

- データセットの単位は「複数フォルダを持つ学習プロジェクト全体」である (例: `kariginu-XL` の `img_v02` 全体)。フォルダ 1 つではない。
- 同じ画像が複数のフォルダに入れる。フォルダごとの学習テキストは別々に保つ。
- 古い版と新しい版は別のデータセットではなく、1 つのデータセットの履歴として扱う。
- 版の継承関係と名称は、取り込み時にユーザー入力で決める。
- 学習設定 json があれば、そこから版などの候補を見つけて初期値に使う。json が無ければ全項目をユーザー入力にする。
- 最初のプロジェクトは、データモデルと移行、取り込み、書き出しの 3 つ。
- 取り込みと書き出しの一致基準は「案C」とする。
  - 取り込み時の元の本文 (`.txt` / `.caption` の中身) を、版の記録として 1 回だけ保存する。版は固めたものなので、後から書き換えない。
  - 取り込んだ版を、編集せずに書き出すときは、記録した元の本文をそのまま出す (完全一致)。
  - 編集した後の書き出しは、学習テキストの要素 (カンマ区切りの 1 つ 1 つ) のデータから組み立てる。要素の中身、並び順、表記 (大文字小文字、アンダースコア、括弧) は取り込み時のまま保つ。空白の数や末尾の改行は変わってよい。
- トリガーワードは、フォルダの属性として持つ。取り込み時に、先頭の要素が共通しているものを自動検出して候補に出し、ユーザーが確認して確定する (自動検出の結果を、確認なしに確定しない)。
  - 最初のプロジェクトでは、保存と候補の表示までを入れる。
  - 書き出しでは、学習テキストを元のまま出す。トリガーワードで書き換えない。
  - 後続: 画像を追加したときの、トリガーワードの自動付与と、付いていない画像の検出。
- 取り込んだタグは、データセットの中 (フォルダ × 画像の学習テキスト) だけに持つ。画像直下の `Tag` には入れない。取り込んだ画像は、普段の画像検索やタグ編集には、タグ付きでは出てこない (画像そのものは `Image` として登録される)。
  - 理由: 同じ画像のフォルダ別の学習テキストが 1 つにまとまるのを防ぐため。
  - 普段のライブラリ側へタグを写す機能は後続とする。
- 取り込むタグの表記は、書き換えない。既存の `TagCleaner.clean_format` (アンダースコアのスペース化、`#` の削除、ピリオドと改行のカンマ化、括弧のエスケープ、連続カンマの統合) は、データセットの取り込みでは使わない。タグへの分割は、カンマと前後の空白の除去だけにとどめる。

## 5. 取り込みダイアログの項目 (私の案)

- どのデータセットの版か (新規作成、または既存から選択) と、版の名前。
- 取り込むフォルダの選択。`sample001/` や `終了/` のような作業用フォルダは外せる。
- 各フォルダの繰り返し回数とフォルダ名。`10_kariginu` のようなフォルダ名から既定値を埋め、ユーザーが直せる。
- 各フォルダのトリガーワード。先頭の要素が共通しているものを候補に出し、ユーザーが確認して確定する。

初期値として出せる候補は次のとおり。

| 項目 | 取得元 | 確かさ (調査結果) |
|---|---|---|
| フォルダ名と繰り返し回数 | フォルダ名の `<回数>_<名前>` | 調査した全データセットで命名が徹底されている |
| 画像枚数 | フォルダ内の画像 | 直下と再帰で枚数が異なる場合がある (XL 旧版: 直下 51、再帰 53) |
| 出力名 | 学習設定 json の `output_name` | 24 設定すべてに存在。同名を複数の設定が共有する |
| 版名の候補 | 出力名・フォルダ名・モデルのファイル名 (`v01`, `_001` など) | 抽出文字列が版・実行番号・改訂番号のどれかは未確認 |
| ベースモデル・解像度 | 学習設定 json | 設定ごとに確認済み |
| トリガーワード | 各フォルダの学習テキストの先頭の要素 | フォルダごとの一致率は 23.8% から 100% まで幅がある。一致率が低いフォルダは候補を出さず、ユーザー入力にする (閾値は、ビルダーが決める) |

## 6. 制約と注意

- DB の `Project` (`lorairo_data/project_name_YYYYMMDD_NNN/`) は、LoRAIro の DB 単位である。新しい「データセット」は、この `Project` とは別の概念として命名し、混同しない。
- `schema.py` の `origin` 列は `CropRelation` のものであり、タグの由来を表す列ではない。タグの由来を持つ列は、現在のスキーマには無い。
- 現状 `Tag` は `Image` に直接ぶら下がっている。要件を満たすには、フォルダごとの学習テキストを画像と別に持つ必要がある。
- 大文字小文字の影響は、学習するモデルによって異なる。
  - CLIP を使う SD1.5、SDXL、Pony、Illustrious 系は、文章を小文字にして読む。`transformers` の CLIP 用トークナイザに小文字化の処理があることを確認した (`tokenization_clip.py`)。SDXL のもう一方のエンコーダは未確認。
  - Anima (Qwen3)、MOSS-Image (Qwen3.5)、P-H3-Image (Qwen3-VL-4B、コミュニティの GGUF 版の記述による) は、言語モデル系のエンコーダを使う。大文字小文字やアンダースコアが学習に影響する可能性があるが、確認していない。Anima の公開情報では、タグは小文字で、アンダースコアではなくスペース区切りとされている。
  - 今回の取り込み対象は Pony 系までだが、今後は上記のモデルも対象になる。そのため、取り込みで表記を書き換えない。
- Kohya はタグを小文字化して数える (`ss_tag_frequency` が小文字になっている理由)。取り込む `.txt` には大文字を含むものがある (XL 旧版で 164 出現)。
- 同名の `.txt` が無い画像の扱い: Kohya の `read_caption` には、画像名の末尾 4 要素を除いた名前の `.txt` を探す処理があるが、今回の候補では該当 0 枚だった。
- 取り込み対象のデータセットは、`H:\` 配下にある。Linux のコンテナからは `/workspaces/LoRAIro` 以下としてしか見えない。実データでの検証は Windows 側で行う。
- スキーマ変更とマイグレーションを伴うため、`.claude/rules/git-workflow.md` に従い worktree と PR で進める。
- DB 設計を含むため、設計判断は ADR (`docs/decisions/`) に残す。

## 7. ビルダーに委ねること

- データセット・版・フォルダのテーブル名、列、制約、インデックスの設計。
- フォルダごとの学習テキストを保持する構造。既存の `Tag` テーブルを拡張するか、別テーブルを作るかを含む。
- 既存データ (通常の画像登録で入ったタグ) の移行方法。
- 取り込みダイアログの具体的な画面設計。
- 元の本文を保存する場所と形式 (版のテーブルに持つか、別テーブルにするか)。
- 版を固める時点の実装 (取り込み時にコピーを作るか、差分で持つか)。
- 「編集していない版」の判定方法 (編集した瞬間に元の本文を使わなくなる、その切り替え)。

## 9.5. 学習パラメーターの保存と書き出し

### 決定済み (ユーザーの決定)

- 学習パラメーターを保存する新しいテーブルを作る。
- 保存した設定は、次の学習に使えるように書き出せるようにする。
- 書き出しの形式は sd-scripts の TOML とする。
- 書き出しの仕様は、sd-scripts のソースを正とする。
- 学習パラメーターは、元の中身と、正規化したものの両方を保存する。テキストなので容量は問題にしない。
- 画像ごとのタグは、最初は文字列のまま持つ。`tag_id` の参照による圧縮は行わない (後から足せる)。
  - 理由: タグ DB は別の DB で外部キー制約がなく、タグ DB の中身が後から変わると、固めたはずの版の中身が変わってしまう。別のマシンにタグ DB が無いと中身を読めなくなる。
  - 容量は、画像ごとのタグを 1 行のテキスト (または配列) にまとめれば抑えられる。取り込んだタグは普段の検索に使わないため、この形で足りる。

### 正規化したものの中身 (私の解釈・ユーザー未確認)

- キー名を sd-scripts の引数名にそろえる (`optimizer` を `optimizer_type` に、など)。
- 値の型を引数の定義に合わせる。
- 空文字のキーを取り除く。
- 秘密の値を取り除く。
- 変換規則がまだ確認できていないキー (画面専用のキー、LyCORIS 27 種) は、変換せず「未変換」の欄にそのまま残す。規則が確認できるまで、これらは TOML に入らない。

### 保存する形 (私の案)

新しいテーブル `training_configs`:

| 列 | 内容 |
|---|---|
| 持ち主 | データセットと、(あれば)版への参照。版は空でもよい |
| 出どころの種類 | Kohya_ss の json、toml、bat、safetensors のヘッダー |
| 元のファイル名 | パスは持たず、ファイル名だけ |
| 元の中身 | 取り込んだ設定を、そのままの文字列で保存 |
| 正規化したもの | 上の「正規化したものの中身」に従って整えた設定 |
| 未変換のキー | 変換規則が未確認のキーと値 |
| 対象スクリプト | `train_network.py` / `sdxl_train_network.py` など。取り込み時に判定して持つ |
| 取り出した主な項目 | 出力名、ベースモデル、解像度、network_dim、network_alpha、学習率 |
| 取り込んだ日時 | |

同じ出力名の設定は、別の行として残す (調整の履歴になる)。

### sd-scripts のソースで確認できたこと (Issue #1404)

対象: 最新の `cb70b96` (2026-10-26)。読んだだけで実行はしていない。

- 構成の TOML (`--dataset_config`): フォルダごとの `image_dir`、`num_repeats`、`caption_extension`、`class_tokens`、`is_reg`。データセット全体の `resolution`、`batch_size`、`enable_bucket` など。
- `caption_extension` の既定値は `.caption`。取り込んだ設定は 24/24 が `.txt` なので、書き出しでは必ず明示する。
- 学習パラメーターの TOML (`--config_file`): キーは引数名そのまま。`[セクション]` の名前は無視される。
- 学習設定 json 24 件のキー 167 種のうち、112 種が引数名と一致する。残り 55 種は、起動ツールの引数 7 種、名前だけが違うもの 7 種、LoRA / LyCORIS の細かい設定 27 種 (`network_args` への詰め替え候補)、画面専用のキー 14 種。
- SD1.5 か SDXL かは、画面専用のキー `sdxl` で決まる (sd-scripts にこの引数は無い)。`sdxl_train_network.py` だけが追加する `--` 引数は、今回の範囲では 0 件だった。

### 書き出しで守ること

- 空文字 (`""`) のキーは出力から除く。sd-scripts は `is None` で判定するため、空文字を渡すと「指定あり」になり、モードが変わる (`dataset_config`、`in_json`)。調査した 24 件には、空文字のキーが 39 種ある。
- 値の型は、引数の定義に合わせて書き出す。元の json では、数値が文字列で入っているキーがある (`learning_rate` は文字列 8 件・小数 16 件)。
- 起動ツール (`accelerate launch`) の引数は TOML に入れない。
- フォルダの場所 (`train_data_dir`、`reg_data_dir`、`output_dir`、`logging_dir`) は、書き出し先に合わせて書き換える。
- 秘密の値 (`wandb_api_key` など) は保存も書き出しもしない (`.claude/rules/security.md`)。取り込み時に値を取り除く。この点は私の判断。

### 未確認

- 画面専用のキー (`LoRA_type`、`sdxl`、`use_wandb`、`lr_warmup`、`max_resolution`、`noise_offset_type` など) が、どの引数へ変換されるかの規則。
- LoRA / LyCORIS 27 種を `network_args` へ詰め替える規則。
- TOML 経由で読んだときの、文字列値の型変換の挙動。
- XL 系 14 件が実際に起動したスクリプト (bat が無く、画面の規則からの推定)。
- 今回調べた 2 系統には `.toml` が 0 件。構成の TOML は新しく作る。

## 10. 私の判断 (ユーザーと未合意・確認用)

ビルダー確認で挙がった点のうち、ユーザーに聞かず私が決めたもの。

- 画像の同一性: `Image` は 1 つのまま、フォルダ × 画像の紐付けでタグを持つ。
- 画像ファイル: 既存の登録経路でコピーする (`save_original_image`、分類が別版/新規のときだけ保存し、重複は既存行へ寄せる)。版ごとの二重保存は起きない。
- 取り込み = 1 つの版を作る。版の取り込みは毎回全量とし、差分取り込みは後続とする。
- 取り込む画像は、各フォルダの直下のみ。Kohya の読み方に合わせたが、この点は未確認。
- 書き出しの拡張子は、取り込んだときの `.txt` / `.caption` を保持して再現する。学習設定 json の書き出しは対象外とする。
- タグの由来: フォルダ側のタグに「Kohya 取り込み」の印を付けるだけにとどめる。サイト保存タグとの区別は後続とする。
- 既存のライブラリ画像をデータセットに追加する機能は後続とする。データセットは 1 つの DB に収まる前提にする。
- テスト用のフィクスチャは、実データの形を再現して作ってよい。実データでの検証は Windows 側で行う。

## 12. 追加の決定 (ユーザーの決定)

- 版の持ち方 (学習パラメーターと、データセットのタグ・フォルダ構成の両方): 版ごとに全量のレコードを持ち、親の版への参照だけを別に記録する。版どうしの比較は表示時に計算する。
- 最初のプロジェクトに、次を含める。
  - 学習パラメーターの保存 (元の中身と正規化したもの)。
  - 構成の TOML (`--dataset_config`) の書き出し。
  - 学習パラメーターの TOML (`--config_file`) の書き出し。ただし、変換するのは、調査した 24 件の設定に実際に出てくる範囲に限る。
    - 名前だけが違うキーの置き換え (`optimizer` を `optimizer_type` に、`max_resolution` を `resolution` に、など)。
    - 意味が置き換わるキー (`use_wandb` を `log_with` に、`lr_warmup` を `lr_warmup_steps` に)。
    - `LoRA_type` が `Standard` と `LyCORIS/LoCon` のものの `network_module` / `network_args` への詰め替え。
  - それ以外の `LoRA_type` (LoHa、LoKr、DyLoRA など) は、変換せず「未変換」の欄に元のまま残す。使う種類が増えたときに足す。
- 変換規則の出どころは、Kohya_ss の操作画面のソース (`kohya_gui/lora_gui.py`、`common_gui.py`、確認した版は `45088f0` / 2026-07-10) と、sd-scripts のソース (`cb70b96` / 2026-10-26)。変換結果は、実際に動いた 24 件の設定と、存在する `.bat` 2 件と突き合わせて確かめる。
