# Kohya-ss 学習データセットの取り込みと書き出し(round trip)設計

調査の経緯と実データの数値は Issue #1404 とそのコメントに残している。本書では、そこから確定した方針と最初のプロジェクトの範囲をまとめる。

## 0. 用語

- **学習テキスト:** データセット側の、画像×フォルダごとの `.txt` または `.caption` の中身。通常の画像タグ(`Tag` テーブル)とは別物である。文章キャプションを格納する既存の `Caption` テーブルと紛らわしいため、「キャプション」とは呼ばない。
- **要素:** 学習テキスト内のカンマ区切りされた 1 つひとつの項目。
- **トリガーワード:** 学習テキストの先頭に共通して付く要素。フォルダ名とは別物であり、フォルダ名からは導出しない。
- **データセット:** 複数のフォルダを持つ学習プロジェクト全体。
- **版:** データセットのある時点の状態を固定したもの。

これらの用語は、設計書内で「通常の画像タグ」と「学習テキスト」を明確に区別するために定義した。この命名は起案者の判断であり、ユーザーとは未合意である。

## 1. 意図と理由

過去に Kohya-ss で学習に使ったデータセットを LoRAIro へ取り込み、後から修正して書き出し直せるようにしたい。修正の頻度は画像の差し替え・追加が最も多く、次にタグの修正である。

手動で整理されたタグは、各サイトから保存した画像とタグに比べて精度と情報量が桁違いに高い。また「何を学習させるためのデータセットか」という目的も明確である。しかし現状の取り込み機能はこれらを活かせていない。

- 画像と同名の `.txt`(タグ)と `.caption`(キャプション)しか読み込まない。
- フォルダ名(`<繰り返し回数>_<名前>`)、学習設定 JSON、モデルのメタデータを読み込まない。
- 保存時のタグは、サイト保存のものも手動整理のものも同じ値(`existing=True`、`is_edited_manually=False`、`model_id=None`、`confidence_score=None`)で登録されるため、取り込み後に区別できない。
- 同一画像(pHash 一致)は重複として既存レコードに集約され、関連ファイルも既存レコードへ取り込まれる。そのため、複数フォルダに同じ画像がある場合、フォルダごとの別々の学習テキストが 1 つの画像に混ざる可能性が高い(コードの記述から読み取った仕様であり、実環境では未検証)。

## 2. ゴール

1. 取り込んだデータセットを、取り込み時と同じ形で書き出せる(round trip)。
2. 同じ画像を複数のフォルダに所属させ、フォルダごとに別の学習テキストを持てる。
3. データセットは複数のフォルダを持てる。
4. データセットは版の履歴を持てる。版は取り込み時点のフォルダ構成と学習テキストの状態を固定したものである。
5. 取り込み時に自動検出した候補を初期値として提示し、ユーザーが確認して確定できる。

## 3. スコープ

### 3.1 最初のプロジェクトに含める(決定済み)

1. **データモデルと移行:** データセット、版、フォルダ、画像×フォルダごとの学習テキストを定義し、Alembic マイグレーションを作成する。
2. **取り込み:** ユーザー入力を伴う取り込みダイアログと、フォルダ構成・学習設定 JSON の読み取りを実装する。
3. **書き出し:** 版を指定して `<繰り返し回数>_<名前>` フォルダと `.txt` の形式で出力する。あわせて sd-scripts 用の TOML(構成と学習パラメーター)を出力する(詳細は §9.5 と §12)。
4. **学習パラメーターの保存:** 新規テーブル `training_configs` を追加する(§9.5)。

### 3.2 後続(最初のプロジェクトに含めない)

5. **編集と版の比較:** フォルダへの画像の追加・差し替え、および版間の差分表示。
   - 想定する運用は、最新の版を元にした作業状態で編集し、確定して新しい版を作る方式である。この方式は起案者の案であり、ユーザーとは未合意である。

### 3.3 非ゴール

- タグ頻度(`ss_tag_frequency`)の突き合わせによる元フォルダの自動特定。
- ファイルの更新日時による版の順序や元フォルダの判定。
- 学習の実行および LoRA 成果物の管理。
- 正則化画像の扱い(調査したすべてのデータセットで存在しなかった)。

### 3.4 アンチゴール

- 生成サンプル画像(`sample001/`)や作業用フォルダ(`終了/`、`__Processed/`)が学習画像として取り込まれること。
- フォルダごとに異なる学習テキストが、画像 1 枚のタグ(画像直下の `Tag`)に混ざること。
- 自動検出の結果をユーザーの確認なしに確定すること。
- 既存のライブラリ機能(検索、アノテーション、通常の画像登録)の挙動が変わること。

## 4. 決定事項(ユーザーの決定)

- **データセットの単位:** フォルダ 1 つではなく、複数フォルダを持つ学習プロジェクト全体(例: `kariginu-XL` の `img_v02` 全体)を 1 データセットとする。
- **画像の複数フォルダ所属:** 同じ画像を複数のフォルダへ入れられるようにし、フォルダごとの学習テキストは別々に保持する。
- **版の履歴管理:** 古い版と新しい版は別データセットにせず、1 つのデータセットの履歴として扱う。版の継承関係と名称は取り込み時のユーザー入力で決める。
- **学習設定 JSON の活用:** 学習設定 JSON がある場合は版名などの候補を抽出して初期値に使う。JSON が無い場合は全項目をユーザー入力とする。
- **最初のプロジェクトの範囲:** データモデルと移行、取り込み、書き出しの 3 点に絞る。
- **取り込みと書き出しの一致基準(案 C):**
  - 取り込み時の元の本文(`.txt` または `.caption` の中身)を版の記録として 1 回だけ保存する。版は固定された記録であるため、後から書き換えない。
  - 未編集の版を書き出すときは、記録した元の本文をそのまま出力する(完全一致)。
  - 編集後の書き出しは、学習テキストの要素(カンマ区切りの各項目)から組み立てる。要素の中身、並び順、表記(大文字小文字、アンダースコア、括弧)は取り込み時のまま保ち、空白の数や末尾の改行のみ変化を許容する。
- **トリガーワードの扱い:** フォルダの属性として保持する。取り込み時に先頭の要素が共通しているものを自動検出して候補に出し、ユーザーが確認して確定する(確認なしに確定しない)。
  - 最初のプロジェクトでは保存と候補表示までを実装する。
  - 書き出しでは学習テキストを元のまま出力し、トリガーワードによる書き換えは行わない。
  - 画像追加時のトリガーワード自動付与と未付与画像の検出は後続とする。
- **タグの隔離:** 取り込んだタグはデータセット側(フォルダ×画像の学習テキスト)のみに保持し、画像直下の `Tag` テーブルには書き込まない。画像は `Image` として登録されるが、通常の画像検索やタグ編集にはタグ付きでは現れない。
  - 理由: 同一画像のフォルダ別学習テキストが 1 つに混ざるのを防ぐためである。
  - 通常ライブラリ側へタグを写す機能は後続とする。
- **表記の無改変:** 取り込むタグの表記は書き換えない。既存の `TagCleaner.clean_format`(アンダースコアのスペース化、`#` の削除、ピリオドと改行のカンマ化、括弧のエスケープ、連続カンマの統合)は使用せず、カンマ分割と前後空白の除去のみにとどめる。

## 5. 取り込みダイアログの項目(起案者の案)

- 対象データセット(新規作成または既存から選択)と版の名前。
- 取り込むフォルダの選択(`sample001/` や `終了/` などの作業用フォルダを除外できる)。
- 各フォルダの繰り返し回数とフォルダ名(`10_kariginu` などのフォルダ名から既定値を埋め、ユーザーが修正できる)。
- 各フォルダのトリガーワード(先頭要素の共通部分を候補として提示し、ユーザーが確認して確定する)。

初期値として提示できる候補は以下のとおりである。

| 項目 | 取得元 | 確かさ(調査結果) |
|---|---|---|
| フォルダ名と繰り返し回数 | フォルダ名の `<回数>_<名前>` | 調査した全データセットで命名が徹底されている |
| 画像枚数 | フォルダ内の画像 | 直下と再帰で枚数が異なる場合がある(XL 旧版: 直下 51、再帰 53) |
| 出力名 | 学習設定 JSON の `output_name` | 24 設定すべてに存在する。同名を複数の設定が共有する |
| 版名の候補 | 出力名、フォルダ名、モデルのファイル名(`v01`、`_001` など) | 抽出文字列が版・実行番号・改訂番号のどれを指すかは未確認 |
| ベースモデル・解像度 | 学習設定 JSON | 設定ごとに確認済み |
| トリガーワード | 各フォルダの学習テキストの先頭要素 | フォルダごとの一致率は 23.8% から 100% まで幅がある。一致率が低いフォルダは候補を出さずユーザー入力とする(閾値は実装者が決める) |

## 6. 制約と注意

- DB の `Project`(`lorairo_data/project_name_YYYYMMDD_NNN/`)は LoRAIro の DB 単位である。新しい「データセット」は `Project` と別概念として命名し、混同しない。
- `schema.py` の `origin` 列は `CropRelation` のための列であり、タグの由来を表すものではない。現行スキーマにタグの由来を持つ列は存在しない。
- 現状 `Tag` は `Image` に直接紐づいているため、要件を満たすにはフォルダごとの学習テキストを画像とは別に保持する必要がある。
- 大文字小文字の扱いは学習対象モデルによって異なる。
  - CLIP を用いる SD1.5、SDXL、Pony、Illustrious 系は文章を小文字化して読む(`transformers` の `tokenization_clip.py` で小文字化処理を確認済み。SDXL のもう一方のエンコーダは未確認)。
  - Anima(Qwen3)、MOSS-Image(Qwen3.5)、P-H3-Image(Qwen3-VL-4B、コミュニティの GGUF 版の記述による)は言語モデル系のエンコーダを用いる。大文字小文字やアンダースコアが学習に影響する可能性があるが未確認である。Anima の公開情報では、タグは小文字かつスペース区切りとされている。
  - 今回の取り込み対象は Pony 系までだが、今後は上記モデルも対象になるため、取り込み時点で表記を書き換えない。
- Kohya はタグを小文字化して集計する(`ss_tag_frequency` が小文字になる理由)。取り込む `.txt` には大文字を含むものが存在する(XL 旧版で 164 出現)。
- 同名の `.txt` が無い画像の扱い: Kohya の `read_caption` には画像名の末尾 4 要素を除いた `.txt` を探す処理があるが、今回の候補データでは該当 0 枚であった。
- 取り込み対象のデータセットは `H:\` 配下にあり、Linux コンテナからは `/workspaces/LoRAIro` 以下しか参照できない。実データでの検証は Windows 側で行う。
- スキーマ変更とマイグレーションを伴うため、`.claude/rules/git-workflow.md` に従いワークツリーと PR で進める。
- DB 設計を含むため、設計判断を ADR(`docs/decisions/`)に記録する。

## 7. 実装者(ビルダー)に委ねること

- データセット、版、フォルダのテーブル名、列、制約、インデックスの設計。
- フォルダごとの学習テキストを保持する構造(既存 `Tag` テーブルの拡張か別テーブル新設かを含む)。
- 既存データ(通常の画像登録で入ったタグ)の移行方法。
- 取り込みダイアログの具体的な画面設計。
- 元の本文を保存する場所と形式(版のテーブルに持つか別テーブルにするか)。
- 版を固定する際の実装方式(取り込み時にコピーを作るか差分で持つか)。
- 「未編集の版」の判定方法(編集した瞬間に元の本文を使わなくなる切り替え方式)。

## 9.5. 学習パラメーターの保存と書き出し

### 決定済み(ユーザーの決定)

- 学習パラメーターを保存する新規テーブルを作成する。
- 保存した設定を次の学習に使える形で書き出せるようにする。
- 書き出し形式は sd-scripts の TOML とし、仕様は sd-scripts のソースを正とする。
- 学習パラメーターは元の中身と正規化後の両方を保存する(テキストデータのため容量は問題視しない)。
- 画像ごとのタグは当初文字列のまま保持し、`tag_id` 参照による圧縮は行わない(後から追加可能)。
  - 理由: タグ DB は別 DB で外部キー制約がないため、タグ DB の変更で固定済みの版が変質する恐れがあり、別マシンにタグ DB が無いと読めなくなる。
  - 容量は画像ごとのタグを 1 行テキスト(または配列)にまとめれば抑えられる。取り込んだタグは通常検索に使わないためこの形式で足りる。

### 正規化後の内容(起案者の解釈・ユーザー未確認)

- キー名を sd-scripts の引数名へ揃える(例: `optimizer` を `optimizer_type` へ)。
- 値の型を引数定義に合わせる。
- 空文字のキーと秘密の値を取り除く。
- 変換規則が未確認のキー(画面専用キー、LyCORIS 27 種)は変換せず「未変換」欄にそのまま残し、規則が確認できるまで TOML へ出力しない。

### 保存する形(起案者の案)

新規テーブル `training_configs`:

| 列 | 内容 |
|---|---|
| 持ち主 | データセットと(あれば)版への参照。版は空でもよい |
| 出どころの種類 | Kohya_ss の JSON、TOML、bat、safetensors のヘッダー |
| 元のファイル名 | パスは持たずファイル名のみ |
| 元の中身 | 取り込んだ設定をそのままの文字列で保存する |
| 正規化したもの | 上記の正規化方針に従って整えた設定 |
| 未変換のキー | 変換規則が未確認のキーと値 |
| 対象スクリプト | `train_network.py`、`sdxl_train_network.py` など(取り込み時に判定して保持) |
| 取り出した主な項目 | 出力名、ベースモデル、解像度、`network_dim`、`network_alpha`、学習率 |
| 取り込んだ日時 | タイムスタンプ |

同じ出力名の設定も調整の履歴として別の行で残す。

### sd-scripts のソースで確認できたこと(Issue #1404)

確認対象は最新の `cb70b96`(2026-10-26)であり、コードリーディングのみで実行は行っていない。

- 構成 TOML(`--dataset_config`): フォルダごとの `image_dir`、`num_repeats`、`caption_extension`、`class_tokens`、`is_reg`、およびデータセット全体の `resolution`、`batch_size`、`enable_bucket` など。
- `caption_extension` の既定値は `.caption` である。取り込んだ設定は 24 件中 24 件が `.txt` であるため、書き出し時は必ず明示する。
- 学習パラメーター TOML(`--config_file`): キーは引数名そのままを使い、`[セクション]` の名前は無視される。
- 学習設定 JSON 24 件のキー 167 種のうち、112 種が引数名と一致した。残り 55 種の内訳は、起動ツール引数 7 種、名前違い 7 種、LoRA / LyCORIS の詳細設定 27 種(`network_args` 詰め替え候補)、画面専用キー 14 種である。
- SD1.5 と SDXL の判別は画面専用キー `sdxl` で決まる(sd-scripts に同引数は無い)。`sdxl_train_network.py` 固有の追加 `--` 引数は今回の範囲では 0 件であった。

### 書き出しで守ること

- 空文字(`""`)のキーは出力から除く。sd-scripts は `is None` で判定するため、空文字を渡すと指定あり扱いになり動作モードが変わる(`dataset_config`、`in_json`)。調査した 24 件には空文字キーが 39 種あった。
- 値の型は引数定義に合わせて書き出す。元 JSON では数値が文字列として入っているキーがある(`learning_rate` は文字列 8 件、小数 16 件)。
- 起動ツール(`accelerate launch`)の引数は TOML に入れない。
- フォルダパス(`train_data_dir`、`reg_data_dir`、`output_dir`、`logging_dir`)は書き出し先に合わせて書き換える。
- 秘密の値(`wandb_api_key` など)は `.claude/rules/security.md` に従い保存も書き出しも行わず、取り込み時に値を取り除く(起案者の判断)。

### 未確認

- 画面専用キー(`LoRA_type`、`sdxl`、`use_wandb`、`lr_warmup`、`max_resolution`、`noise_offset_type` など)から各引数への変換規則。
- LoRA / LyCORIS 27 種を `network_args` へ詰め替える規則。
- TOML 経由で読み込んだ際の文字列値の型変換挙動。
- XL 系 14 件で実際に起動されたスクリプト(bat ファイルが無く、画面の規則からの推定にとどまる)。
- 今回調査した 2 系統には `.toml` が 0 件であり、構成 TOML は新規に作成する。

## 10. 起案者の判断(ユーザーと未合意・確認用)

ビルダー確認で挙がった論点のうち、ユーザーへ確認せず起案者が決めた項目は以下のとおりである。

- **画像の同一性:** `Image` は 1 レコードのまま維持し、フォルダ×画像の紐づけ側で学習テキストを持つ。
- **画像ファイル:** 既存の登録経路(`save_original_image`)でコピーする。新規または別版の場合のみ保存し、重複は既存行へ集約するため、版ごとの二重保存は起きない。
- **取り込み単位:** 1 回の取り込みで 1 つの版を作成する。毎回全量取り込みとし、差分取り込みは後続とする。
- **画像探索範囲:** 各フォルダの直下のみを対象とする。Kohya の読み込み仕様に合わせたが未確認である。
- **書き出し拡張子:** 取り込み時の `.txt` または `.caption` をそのまま再現する。学習設定 JSON の書き出しは対象外とする。
- **タグの由来:** フォルダ側の学習テキストに「Kohya 取り込み」の印を付けるだけにとどめ、サイト保存タグとの区別は後続とする。
- **既存ライブラリ画像の追加:** 後続機能とする。データセットは 1 つの DB に収まる前提とする。
- **テストフィクスチャ:** 実データの構造を再現したフィクスチャでテストし、実データでの検証は Windows 側で行う。

## 12. 追加の決定(ユーザーの決定)

- **版の持ち方(学習パラメーターおよびデータセットのタグ・フォルダ構成の両方):** 版ごとに全量レコードを保持し、親版への参照のみ別途記録する。版間の比較は表示時に計算する。
- **最初のプロジェクトに含める範囲:**
  - 学習パラメーターの保存(元の中身と正規化後の両方)。
  - 構成 TOML(`--dataset_config`)の書き出し。
  - 学習パラメーター TOML(`--config_file`)の書き出し。変換対象は調査した 24 件の設定に実際に出現する範囲に限定する。
    - 名前のみ異なるキーの置換(`optimizer` → `optimizer_type`、`max_resolution` → `resolution` など)。
    - 意味が置き換わるキーの変換(`use_wandb` → `log_with`、`lr_warmup` → `lr_warmup_steps`)。
    - `LoRA_type` が `Standard` および `LyCORIS/LoCon` の場合の `network_module` と `network_args` への詰め替え。
  - その他の `LoRA_type`(LoHa、LoKr、DyLoRA など)は変換せず「未変換」欄にそのまま残し、利用する種類が増えたタイミングで追加する。
- **変換規則の根拠:** Kohya_ss 操作画面のソース(`kohya_gui/lora_gui.py`、`common_gui.py`、確認版 `45088f0` / 2026-07-10)と sd-scripts のソース(`cb70b96` / 2026-10-26)を根拠とする。変換結果は実稼働した 24 件の設定および 2 件の `.bat` ファイルと突き合わせて検証する。
